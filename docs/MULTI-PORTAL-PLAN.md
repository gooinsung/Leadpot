## 1. 배경 · 목표

현재 리드팟은 **마케터**가 폼/랜딩을 만들어 리드를 수집하는 단일 포털이다. 여기에 두 종류의 사용자·화면을 추가한다.

| 포털 | 도메인(예) | 사용자 | 핵심 목적 |
|---|---|---|---|
| **마케터 포털** (기존) | `app.도메인` | 마케터(리드 공급자) | 폼/랜딩 제작, 리드 수집, **광고주에게 리드 공급(배정)** |
| **광고주 포털** (신규) | `client.도메인` (가칭) | 광고주(리드 구매자) | 공급받은 리드를 **실시간 확인·처리**(승인/거절/메모/상태) |
| **관리자 포털** (신규) | `admin.도메인` (가칭) | 리드팟 운영자 | **모든 데이터·사용자·정산·품질** 관리 |

> 핵심 전환: "폼으로 내 리드를 모은다" → "마케터가 만든 리드를 광고주에게 **공급/판매**하고, 광고주가 그 리드를 **소비/검수**한다." 즉 **리드 유통(distribution) 모델**.

## 2. 핵심 새 개념 (도메인 모델)

기존: `User`(마케터) → `Form`/`LandingPage`(owner_id) → `Lead`(form_id). 리드는 마케터 소유.

추가해야 할 개념:

1. **광고주(Advertiser)** — 리드를 공급받는 주체. 계정으로 로그인.
2. **연동/배정 규칙(Assignment / Campaign)** — "어떤 리드폼(또는 캠페인)의 리드를 어떤 광고주에게 보낼지".
3. **리드 배정(Lead Assignment)** — 리드 1건이 광고주에게 공급된 사실 + **광고주 관점의 처리 상태**(승인/거절/메모). ⭐ 마케터의 원본 리드는 그대로 두고, 광고주별 처리 상태를 **별도 레코드**로 관리(재배정·다중배정·반려 대응).
4. (선택/후기) **정산(Billing/Settlement)** — 리드 단가, 광고주 청구, 마케터 지급, 반려분 제외.

### 리드 흐름
```
방문자 → 공개 폼 제출 → Lead 생성(마케터 소유)
   └─ 배정 규칙에 따라 → LeadAssignment 생성(광고주에게 공급)
        └─ 광고주 포털에서 확인 → 승인/거절/메모 (+ 반려 시 정산 제외)
```

## 3. 포털별 필요 기능 (사용자가 말한 것 + 내가 검토해 추가한 것)

범례: ⭐=MVP 후보 · ➕=사용자 요청 외에 내가 추가 제안 · 🔒=외부/유료 리소스

### 3-A. 마케터 포털 (기존 + 추가)
- ⭐ **리드폼 ↔ 광고주 연동**: 폼(또는 캠페인)에 공급 대상 광고주 지정. (사용자 요청)
- ➕ **배정 규칙**: 단일 광고주 / 다중 광고주 분배(순번·비율·수량 쿼터·지역 등 — 기존 BACKLOG F2 "DB 자동배정"과 연결).
- ➕ **공급 현황 대시보드**: 광고주별 공급 수·승인율·반려율.
- ➕ **반려(claim) 수신·대응**: 광고주가 반려한 리드 확인·재배정·이의.
- ➕ **광고주 초대**: 마케터가 광고주 계정 초대(또는 관리자만 생성 — §9 결정).

### 3-B. 광고주 포털 (신규)
- ⭐ **공급받은 리드 실시간 목록/상세** (배정된 것만 — 강력한 데이터 격리). (사용자 요청)
- ⭐ **처리: 승인 / 거절 / 메모** + 광고주 관점 상태(접수→확인→승인/거절/보류→완료). (사용자 요청)
- ⭐ **CSV/엑셀 다운로드** (기존 기능 재사용, 배정분만).
- ➕ **반려(claim) 신청**: 불량/중복/허수 리드 반려 사유 제출 → 정산 제외·마케터 통지. (리드-젠 업계 필수)
- ➕ **검색·필터·중복 표시** (기존 리드 관리 기능을 광고주 스코프로 재사용).
- ➕ **실시간 알림**: 새 리드 배정 시 텔레그램/이메일/카톡(기존 연동 기반, 광고주별 설정).
- ➕ **외부 CRM 웹훅/ API 연동**(BACKLOG F7): 광고주가 자사 시스템으로 리드 pull/push.
- ➕ **개인정보 노출 범위 제어**: 계약에 따라 특정 필드 마스킹(예: 승인 전 전화 뒤 4자리 가림).
- ➕ (정산 도입 시) **잔액·충전·명세서**.

### 3-C. 관리자 포털 (신규)
- ⭐ **전체 사용자 관리**: 마케터·광고주 CRUD, 승인/정지, 역할 부여.
- ⭐ **전체 데이터 조회**: 모든 폼/랜딩/리드/배정/캠페인.
- ➕ **캠페인·단가·계약 관리**: 광고주↔마케터↔단가 매핑.
- ➕ **정산 관리**: 승인 리드 집계, 청구/지급, 반려 조정, 명세서 발행.
- ➕ **품질·분쟁 중재**: 반려(claim) 승인/기각, 어뷰징(허수·봇) 모니터링.
- ➕ **플랫폼 통계**: 유입·전환·매출·마케터/광고주별 실적.
- ➕ **감사 로그(audit log)**: 누가 무엇을(리드 조회·상태변경·정산) 했는지 — 개인정보 취급 추적.
- ➕ **전역 설정·공지**, 전역 IP/봇 차단.

## 4. 데이터 모델 스케치 (Flyway 신규 마이그레이션)

> 원칙: 기존 테이블(users/forms/leads…)은 최대한 보존하고 **추가 테이블 + 컬럼**으로 확장.

- **users.role 확장**: 현재 `USER|ADMIN` → `MARKETER | ADVERTISER | ADMIN`(+ 필요시 SUPER_ADMIN). 기존 USER=MARKETER 로 백필.
  - 대안: 별도 `advertisers` 테이블 대신 users 재사용(권장 — 인증·계정 로직 공유). 광고주 부가정보는 `advertiser_profile`(회사명·사업자·연락처 등) 분리.
- **campaigns** (선택, 배정 상위 개념): id, advertiser_id, marketer_id, name, unit_price, status, quota…
- **form_assignments**: form_id ↔ advertiser_id(또는 campaign_id) + 배정 규칙(rule, quota, ratio). "이 폼의 리드를 이 광고주에게".
- **lead_assignments** ⭐(핵심): id, lead_id, advertiser_id, assigned_at, **advertiser_status**(NEW/CONFIRMED/APPROVED/REJECTED/HOLD/DONE), rejected_reason, price_snapshot, claim_status…
  - 광고주 메모는 기존 `lead_notes` 를 재사용하되 **스코프(작성자·가시성)** 추가(마케터 메모/광고주 메모 구분).
- **lead_claims**(반려/분쟁): id, lead_assignment_id, reason, status(REQUESTED/APPROVED/REJECTED), resolved_by, resolved_at.
- **(정산 도입 시) billing**: advertiser_balance, transactions, invoices…
- **audit_logs**: actor_id, role, action, target_type, target_id, at, ip.

접근 격리(row-level): **광고주는 자신이 advertiser_id 인 lead_assignments(→ 그 lead)만** 조회. 마케터는 자기 owner 리소스만. 관리자는 전체. (기존 K5 원칙을 배정 축으로 확장)

## 5. 보안 · 데이터 격리 (매우 중요)

- 리드는 **개인정보**다. 포털·역할별 접근을 서버에서 강제(클라이언트 신뢰 금지).
  - 광고주 API: JWT의 role=ADVERTISER + 요청 리소스가 본인 배정분인지 항상 검증.
  - 관리자 API: role=ADMIN 필수 + **감사 로그** 필수.
- **개인정보 마스킹** 정책: 광고주가 승인 전/후 볼 수 있는 필드 범위(계약 기반).
- 관리자 코드/화면이 광고주·마케터 번들에 섞이지 않도록 **프론트 분리**(§7).
- 3개 도메인 → CORS 오리진·쿠키/토큰 스코프 정리. 토큰에 role 클레임 포함(이미 JWT 사용).

## 6. 기존 기능 재사용 포인트

- **리드 상세/메모/태그**(이번에 구현): 광고주 포털에서 스코프만 바꿔 재사용.

- **CSV/엑셀·중복표시·검색필터**: 배정 스코프로 재사용.

- **서브도메인 라우팅(D3)**: 이미 공개 페이지에 도입 → 포털 라우팅 설계에 참고.

## 7. 아키텍처 결정 — 새 프로젝트 vs 멀티모듈 vs 단일 경로 분리

### 후보
| 안 | 구성 | 장점 | 단점 |
|---|---|---|---|
| A. 완전 별도 3프로젝트 | 포털별 프론트+백엔드 각각 | 완전 격리 | **DB·리드·인증을 공유해야 하는데** 백엔드 3개면 데이터 정합성·중복 로직·인증 동기화 비용 폭증. 비권장. |
| B. 모노레포 · 단일 백엔드 · 멀티 프론트 | 저장소 1개. 백엔드 1개(역할 기반 인가, 도메인별 패키지). 프론트 앱 3개(공통 lib 공유) | 데이터/인증 단일 소스, 포털별 UX·번들·배포 분리, 관리자 코드 격리 | 프론트 빌드 타깃 3개 관리 |
| C. 단일 백엔드 · 단일 SPA(경로/서브도메인 분기) | 지금 구조 유지, 라우트로 포털 분기 | 가장 빠른 시작 | 관리자/광고주 코드가 한 번들에 → 보안·비대화, UX 타협 |

### 추천 ✅ = **B (모노레포 + 단일 백엔드 + 포털별 프론트 앱)**
- **백엔드는 반드시 하나.** 세 포털이 **같은 리드/폼/배정 데이터**를 공유하므로 단일 API + **역할 기반 인가**가 정답. 도메인이 커지면 패키지(`advertiser`, `admin`, `campaign`, `billing`)로 정리하고, 더 커지면 Gradle **멀티모듈**(공통 도메인 모듈 + 포털별 web 모듈)로 승격 가능 — 처음부터 멀티모듈로 과설계할 필요는 없음.
- **프론트는 포털별로 분리 배포.** 저장소 안에 `frontend/`(마케터, 기존), `advertiser/`, `admin/` 앱을 두고 **공통 코드(api client·타입·디자인 토큰·컴포넌트)는 shared 패키지**로. 각 앱 = 각 도메인 = Cloudflare Pages 프로젝트. → 관리자 코드가 광고주에게 안 나가고, 도메인별 env·배포 독립.
- 초기 단계에선 C(단일 SPA 분기)로 광고주 포털을 빠르게 프로토타이핑한 뒤 B로 분리하는 점진 전환도 가능. 단, **관리자 포털은 처음부터 분리**(보안).

> 요약: **한 저장소 · 백엔드 1개(역할 기반, 패키지 분리) · 프론트 3앱(공통 lib). 완전 별도 프로젝트는 비권장.**

## 9. 착수 전 결정 필요 (사용자 확인)

1. **비즈니스 모델**: 정산/과금(리드 단가·청구·지급)을 **범위에 포함**하나, 아니면 "실시간 확인·처리"만 먼저? (정산 포함 여부가 데이터 모델을 크게 좌우)
2. **광고주 계정 생성 방식**: (a) 관리자가 생성/승인 (b) 마케터가 초대 (c) 자가가입+승인. 
3. **배정 단위**: 리드폼 단위 1:1 광고주 / 캠페인 단위 / 다중 광고주 분배(F2)까지?
4. **반려(claim) 정책**: 반려 허용 여부·사유·기한·정산 반영 방식.
5. **개인정보 노출 범위**: 광고주가 보는 필드·마스킹 정책(승인 전/후).
6. **한 사람이 마케터이면서 광고주**일 수 있나(역할 겸직)?
7. **도메인 네이밍**: `client` / `advertiser` / `partner` 중 무엇? 관리자 `admin`?
