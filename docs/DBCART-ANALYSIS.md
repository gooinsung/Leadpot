# docs/DBCART-ANALYSIS.md — 실제 디비카트 구조 분석 (로그인 후)

> 실제 계정으로 로그인해 관리자 화면 전체를 돌아보며 역설계(reverse engineering)한 결과.
> 우리 서비스의 데이터 모델·화면 설계의 근거 자료.

## 1. 전체 구조 한눈에

- **최상위 단위 = "랜딩(landing)"**. 계정 1개에 여러 랜딩을 두고, 랜딩을 **그룹**으로 조직한다.
- 화면은 "**랜딩 하나를 선택**"한 뒤, 그 랜딩에 대해 꾸미기/리드/통계/설정/결제를 다루는 구조.
- **결제·서비스 만료·도메인·폼·리드·통계·차단이 전부 "랜딩 단위"**로 관리됨(요금도 랜딩별 결제).
- 부가 서비스는 별도 앱: **파티**(`pt.dbcart.net`, 계정 간 데이터 공유), **팀플**(`tp.dbcart.net`, 팀 CRM).

### 사이트맵 (관리자)
```
[상단 전역] 랜딩관리 · 디비내역 · 유입/접수 카운터 · 내정보 · 샘플보기 · 이용요금 · 고객센터 · 이벤트 · 파티 · 팀플 · 로그아웃

[좌측 = 선택된 랜딩 기준]
├─ 랜딩그룹            /group.html          랜딩 묶음 관리
├─ 나의랜딩/랜딩추가/랜딩변경                랜딩 선택·생성·전환
├─ 디비내역            /db.html             수집 리드 관리
├─ 접속통계            /state.html          방문/전환 통계
├─ 유입경로            /connect_url.html    리퍼러 유입 분석
├─ 랜딩 홍보하기       /landing_pr.html     퍼가기/SNS/검색등록/픽셀
├─ 랜딩꾸미기          /landing_setup.html  ★ 빌더(폼 포함)
├─ 랜딩기본정보        /landing_info.html   ★ 랜딩 설정(탭 6개)
├─ 랜딩접속차단        /landing_ip.html     IP/Agent/문자 차단
├─ SMS/알림관리        /sms.html            문자·앱·카카오 알림
└─ 결제내역            /payment_info.html   랜딩별 결제
```

## 2. 랜딩꾸미기(빌더) 구조 — `/landing_setup.html`

탭: **템플릿 선택 / 상세설정 / 플러그인**

- **상단 꾸미기**: 타이틀, 브라우저 창 제목, 상단 퀵링크(제목+신청버튼 고정 바), **상단 이미지(폼 위로 여러 장)**, 상단 텍스트
- **폼 꾸미기**: 폼 모양, 입력박스 돋보이기
  - 폼 항목 테이블 컬럼: **사용 / 폼번호(순서) / 이름 / 유형 / 설명 / 필수유무 / 중복유무**
  - **필드 유형 17종**: 단순입력, 전화번호, 휴대폰번호, 휴대폰(010고정), 휴대폰`인증`(010), 라디오, 라디오(버튼형), 체크박스, 셀렉트, 날짜, 이메일, 주소, 지역선택, 내용(textarea), 숫자만, 한글만, 길이제한
  - 동의 항목: 이용약관 / 개인정보 수집 / 광고성 정보 수신 / 제3자 제공 / 전체동의 자동표시
  - 신청 버튼: 이름 + 색상
- **하단 꾸미기**: 하단 이미지(여러 장), 카피라이트(글자 크기/정렬/굵기)
- 저장/취소, **간편 모드** 토글
- **공개 URL**: `{숫자ID}.dbcart.net` 형태의 **서브도메인** (예: `1784785934139289.dbcart.net`)

> 즉 랜딩 = **[상단 이미지들] + [폼] + [하단 이미지들]** 의 수직 조립. "블록 빌더"라기보다 **상단/폼/하단 3영역 + 이미지 나열 + 폼 항목 구성** 모델.

## 3. ★ 폼 재사용 관련 결론

| 질문 | 실제 디비카트 |
|---|---|
| 폼 1개 만들어 여러 랜딩에서 불러쓰기(폼 인스턴스 공유)? | **아니오.** 폼은 랜딩마다 랜딩꾸미기 안에서 개별 구성. 전역 "폼 라이브러리" 없음 |
| 필드 유형 재사용? | **예.** `입력폼 유형관리`(/landing_form_type.html)에서 **커스텀 입력폼 유형(필드 타입)을 만들어 재사용** |
| 폼을 외부에서 재사용? | **예.** 홍보하기의 `입력폼 퍼가기`로 폼을 외부 사이트/블로그에 **임베드** |

→ 디비카트는 "**필드 타입 재사용 + 폼 외부 임베드**"는 지원하되, "하나의 폼을 여러 랜딩에 공유"하는 구조는 아니다. (랜딩 복제로 유사 효과는 가능할 수 있음 — 미확인)

## 5. 디비내역(리드) — `/db.html`

- 수집 ON/OFF 토글
- 필터: 전체/오늘/지난7일/지난30일/기간, **그룹**, **처리분류(대기/정상/불량)**
- 검색: 이름 / 연락처 / IP / Agent
- 액션: 선택 삭제, **선택 상태 일괄 변경**(대기/정상/불량), 페이지 크기(10~500), **엑셀 다운로드 / 항목별 엑셀 다운로드**
- 컬럼: 신청일 / 이름 / 연락처 / **추가필드(동적)** / IP / 그룹 / 처리분류 / 관리

## 6. 통계 — `/state.html`

탭: **일별현황 / 상세현황 / 마케팅통계(UTM) / 이미지 노출현황 / 성과 비교**
- 지표: 유입(PC/모바일/전체), 접수(PC/모바일), **접수율(전환율)**, 주간/야간 구분, 최근 10일 그래프, 엑셀 다운로드

## 7. 홍보하기 — `/landing_pr.html`

탭: 랜딩주소 퍼가기 / **입력폼 퍼가기(외부 임베드)** / SNS 홍보 / **검색엔진 등록(사이트맵)** / **픽셀관리(페북·카카오·구글애드워즈·틱톡 ID 입력)**

## 8. 접속차단 — `/landing_ip.html`

탭: **IP 차단(와일드카드 `1.2.3.*`)** / 디비접수 문자 차단 / **에이전트(User-Agent) 차단** / 차단·중복 메시지 설정

## 9. 알림 — `/sms.html`

탭: SMS발송내역 / SMS설정 / **APP 알림설정** / 카카오 발송내역 / **카카오 알림설정** / **휴대폰 번호 인증 설정** / **신청자 SMS(발송내역/설정)** — 모두 **크레딧(사용가능 건수)** 방식
- 관리자 알림(SMS/앱/카카오) + 신청자에게 SMS + 폼의 휴대폰 인증

## 10. 계정 — `/member_info.html`

탭: 내정보 / 계정 환경 설정 / **로그인 기록**
- SNS 가입 지원(네이버 등), 파티키, **계정 접속 제어(모든 세션 강제 로그아웃)**, 회원탈퇴

## 11. 우리 설계에 주는 시사점

1. **랜딩(landing)을 중심 애그리거트로.** 계정 1:N 랜딩, 랜딩을 그룹으로 묶음. 폼·리드·통계·설정·결제가 랜딩에 매달림. (현재 우리 데이터 모델과 방향 일치)
2. **폼 = 랜딩 종속 + 필드 배열**(순서/유형/필수/중복). 필드 유형은 별도 재사용 가능(선택 기능).
3. **리드 처리분류 = 대기/정상/불량**(스팸 분류) — 우리 `leads.status`에 반영 권장. CRM 상담단계(팀플)는 별개 축.
4. **추가필드(동적 컬럼)** — 폼 항목이 가변이므로 리드 값은 JSON(`values_json`)로 저장하는 게 맞음(Postgres JSONB 적합).
5. **외부 연동 = 웹훅(NOTI, 예약어 치환) + 구글시트 + 연결키(파티/팀플)**. 우리도 웹훅을 2차 기능으로.
6. **마케팅 = 픽셀ID 관리 + 커스텀 스크립트 주입 + UTM + 사이트맵 + 폼/URL 임베드**.
7. **중복/스팸 방지 = IP·쿠키·폼값 중복(개수·기간) + IP/Agent/문자 차단 + 해외차단 + 휴지통**.
8. **공개 URL = 서브도메인 + 커스텀 도메인(CNAME)**. 우리는 초기 `/{slug}` 경로 → 이후 서브도메인/커스텀 도메인 확장.

## 12. 미확인/추가 확인 필요

- 랜딩 복제(추가 시 기존 랜딩 복사) 지원 여부
- 정책관리/유입경로/템플릿(landing_template) 상세 화면
- 팀플(tp)·파티(pt) 앱 내부 상세 (별도 로그인 필요할 수 있음)
