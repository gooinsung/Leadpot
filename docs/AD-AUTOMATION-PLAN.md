## 1. 무엇을, 왜

마케터가 자기 광고 계정(당근·메타·구글)을 리드팟에 연결해 두면, **리드폼에 들어온 리드 수 같은 '조건'을 만족했을 때
선택한 '동작'(캠페인 끄기 등)을 리드팟이 대신 실행**한다. 예: "리드폼 A 에 오늘 5건 들어오면 메타·당근 캠페인을 끈다."

- **편의 기능이다.** 리드팟 본 서비스(리드 접수·알림·전달·통계)와 **철저히 무관**해야 한다 — 매체 API 가 죽든,
  이 기능에 버그가 있든 리드 접수는 한 건도 영향을 받으면 안 된다(사용자 원칙, 2026-11-19).
- **확장 전제**: 조건(일 수량 → 주 수량·CPA·시간대 …)과 동작(캠페인 끄기 → 예산 증감 …), 매체(당근·메타·구글 →
  카카오·네이버·토스 …)가 계속 늘어난다. 새 종류를 **하나 추가하는 것만으로** 붙어야 한다.

## 3. 접근 방식 (검토한 대안)

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 같은 서버 안 독립 모듈** ✅ | 본체는 모듈을 모르고, 접수 커밋 후 신호 1개만 보낸다 | 운영 대상이 지금처럼 1개. 경계가 명확해 나중에 별도 서버로 떼기도 쉽다 |
| B. 처음부터 별도 서버 | Railway 서비스 추가 | 격리는 최강이나 배포·감시·비용 2배. 같은 DB 를 써야 해서 이득 대비 과함 |
| C. 매체 네이티브 규칙(메타 adrules) | 메타가 직접 평가 | 메타만 됨·리드팟 리드 수를 모름 → 공통 구조 불가. 제외 |
| 감지 방식 (a) 1분마다 직접 세기 | 본체 무수정 | 사용자가 (b) 선택 — 즉시 반응 |
| 감지 방식 (b) 접수 후 호출 ✅ | 커밋 후 비동기 | 본체 수정은 호출 1줄. 아래 §5 로 안전 보장 |

## 4. 구조

```
LeadService.submit()  ── 커밋 후 ──▶ AdAutomationTrigger.onLeadSubmitted(formId)   ← 본체가 아는 유일한 것
                                         │ (전용 스레드 1개, 대기열 상한, 예외 전부 삼킴)
                                         ▼
                                   AdRuleEngine ── 규칙 조회(리드폼) → 조건 평가 → 기간당 1회 선점
                                         │
                       ┌─────────────────┴─────────────────┐
                 RuleCondition(종류별)               RuleAction(종류별)
                 · DAILY_LEAD_COUNT (1차)            · PAUSE_CAMPAIGNS (1차)
                 · (주 수량·CPA·시간대 …)            · (예산 증감·켜기 …)
                                                         │
                                                  AdPlatformClient(매체별 어댑터)
                                                  · KARROT (1차) · META · GOOGLE · (…)
                                                         │
                                       AdActionLog(실행 이력) + 텔레그램 알림
```

### 4-1. 패키지 `com.leadpot.adautomation`
- `platform/` — 매체 어댑터 공통 계약.
  - `AdPlatform`(enum: KARROT·META·GOOGLE), `AdPlatformClient`(연결 확인·광고계정 목록·캠페인 목록·캠페인 켜기/끄기),
    `AdPlatformException`(종류: 인증 무효·호출 한도·대상 없음·일시 오류·기타), `AdPlatformClients`(enum → 구현체).
  - 매체별 구현은 `platform/karrot/` 처럼 **하위 패키지 하나에 가둔다** — API 버전이 바뀌어도 그 폴더만 고친다.
  - 모든 호출은 `java.net.http.HttpClient`(연결 5초·요청 10초 제한). **매체 SDK 를 쓰지 않는다.**
- `connection/` — 매체 연결(마케터 소유). 자격증명은 **AES-GCM 암호화**해 저장(`CredentialCipher`).
  - 연결 1개 = 인증 단위. 당근은 키 1개 = 광고계정 1개, 메타는 토큰 1개 = 광고계정 여러 개, 구글은 로그인 1번 = 여러 개.
  - 광고계정·캠페인 목록은 **저장하지 않고 필요할 때 매체에서 조회**한다(1차 단순화).
- `rule/` — 규칙 = 리드폼 1개 + 조건(종류+설정 JSON) + 동작(종류+설정 JSON) + 대상 캠페인 N개.
  - `RuleCondition`·`RuleAction` 인터페이스 + 종류별 구현을 스프링 빈으로 등록 → **새 종류 = 클래스 1개 추가**.
  - 기간당 1회: `UPDATE ad_rules SET last_fired_period=:p WHERE id=:id AND last_fired_period IS DISTINCT FROM :p`
    가 1행일 때만 실행(동시 접수 2건이 같은 순간 와도 한 번만 발동).
- `run/` — 실행 이력(`ad_action_logs`) + 알림(`AdNotifier`: 마케터 텔레그램, 기존 `NotificationService.sendTelegram` 재사용).
- `AdAutomationController` — `/api/ad-automation/**`(마케터 전용, SecurityConfig 의 `/api/**` = ROLE_USER 그대로).

### 4-2. DB (V49, 새 테이블만 — 기존 테이블 변경 0)
- `ad_connections`(owner_id, platform, label, credentials_enc, status ACTIVE/INVALID, status_message, …)
- `ad_rules`(owner_id, form_id, name, enabled, paused_reason, condition_type, condition_config jsonb,
  action_type, action_config jsonb, notify_success, last_fired_period, last_fired_at, …)
- `ad_rule_targets`(rule_id, connection_id, account_id, campaign_id, campaign_name)
- `ad_action_logs`(owner_id, rule_id, trigger RULE/MANUAL, connection_id, platform, account_id, campaign_id,
  campaign_name, action, success, message, created_at)
- ⚠️ `ad_rules.form_id` 에는 **FK 를 걸지 않는다** — 걸면 리드폼 삭제가 규칙 때문에 막히거나(RESTRICT) 규칙이 조용히
  사라진다(CASCADE). 결정대로 "일시정지 + 표시"를 하려면 FK 없이 엔진이 존재를 확인한다. `owner_id` 만 users FK.

### 4-3. 화면
- 사이드 메뉴 '운영' 섹션에 **"광고 연동"** → 탭: 매체 연결 / 캠페인(수동 켜기·끄기) / 자동화 규칙(+실행 이력).
- **당근 연동 안내 페이지**(`/ad-automation/guide/karrot`) — 키 발급 절차, 전문가모드 전용, 재발급 시 기존 키 폐기 주의.

## 5. 🔴 기존 서비스 영향 · 서버 부하 검토 (2026-11-19, 코드 실측 기반)

### 5-1. 리드 접수에 미치는 영향 — **없게 설계**
| 위험 | 실제 코드 | 대응 |
|---|---|---|
| 매체 호출이 접수를 느리게 함 | `submit()` 은 `@Transactional` 동기 처리 | 접수 스레드에서 **매체 호출·DB 조회 0**. 커밋 후 **전용 스레드**로 넘기기만 한다 |
| 우리 코드 예외가 접수를 실패시킴 | 같은 트랜잭션 안에서 예외가 나면 롤백 | 호출부 전체를 `try/catch(Throwable 제외 RuntimeException)`로 감싸고, 실제 일은 **커밋 이후**(`TransactionSynchronization.afterCommit`)에만 한다 — 이미 `NotificationService.runAfterCommit` 이 같은 방식으로 운영 중 |
| 접수가 롤백됐는데 동작 실행 | — | 커밋 후에만 실행하므로 롤백된 접수는 신호도 안 간다 |
| 스레드·메모리 폭주 | 기존 executor 들은 대기열 무제한(`Executors.newSingleThreadExecutor`) | **전용 스레드 1개 + 대기열 상한 500**, 넘치면 버리고 경고 로그. 버려도 다음 접수 때 다시 평가되므로 안전 |
| `LeadService` 생성자 변경이 테스트를 깸 | `new LeadService(` 직접 생성하는 곳 **0곳**(스프링 주입만) | 생성자 파라미터 1개 추가로 끝 |

### 5-2. DB 커넥션 풀(Hikari 최대 10)
- 접수 1건당: 전용 스레드에서 **규칙 존재 확인 쿼리 1회**(form_id 인덱스). 규칙 없는 리드폼은 여기서 끝.
- 규칙 있는 리드폼: + 오늘 건수 count 1회(leads 의 기존 form 인덱스) + 발동 시 선점 UPDATE 1회 + 이력 INSERT.
- **매체 HTTP 호출 중엔 DB 커넥션·트랜잭션을 잡지 않는다**(조회 트랜잭션 → 커밋 → HTTP → 새 트랜잭션으로 이력 저장).
  스레드가 1개라 이 기능이 동시에 쥐는 커넥션은 **최대 1개**.

### 5-3. CPU·메모리·네트워크
- 타이머 없음(1차는 접수 때만 동작). 매체 호출은 규칙 발동 시 캠페인 수만큼(하루 몇 번).
- 화면에서 캠페인 목록 조회는 마케터가 탭을 열 때만. 당근 한도(분당 60회, 계정 단위)에 여유가 크다.
- 새 라이브러리 **0개**(JDK HttpClient + 이미 있는 Jackson). 이미지 크기·기동 시간 영향 없음.

### 5-4. 장애 격리
- 끄는 스위치: `APP_AD_AUTOMATION_ENABLED=false` → 신호를 받자마자 무시(수동 버튼도 막힘). 재배포만으로 즉시 차단.
- 암호화 키(`APP_AD_CREDENTIALS_KEY`)가 없으면 **서버는 정상 기동**하고, 매체 연결 저장만 "서버 설정 필요"로 거절한다.
- 매체 실패 → 이력에 실패 기록 + 마케터 텔레그램 → 끝(재시도 없음, 결정 13). 인증 무효면 연결 상태를 INVALID 로 바꾼다.

### 5-5. 보안
- 고객 광고계정 키는 리드팟이 보관하는 정보 중 **가장 민감**하다 → AES-256-GCM(키는 Railway 환경변수만),
  API 응답·로그·화면에 **원문 미노출**(마지막 4자리만).
- 모든 조회·조작은 `owner_id` 로 본인 것만(다른 마케터의 연결·규칙·캠페인 접근 불가).

### 5-6. 남는 위험(알고 가는 것)
- **5건에서 정확히 멈추지 않는다** — 매체 반영 지연(당근 최대 30분 명시, 메타·구글 수 분) 동안 들어오는 리드는 막지 못한다(결정 2: 광고만 끈다).
- 백엔드가 여러 대가 되면 선점 UPDATE 로 중복 발동은 막히지만, 그 외 스케줄 작업(기존 리포트 등)과 함께 재검토.
- 당근 OpenAPI 는 **베타**(v0.7.0, 거의 매달 변경) — 어댑터 한 곳만 영향.

### 5-7. 검증 결과 (2026-11-19, 원격 세션)
- 백엔드 전체 테스트 **398건 통과**(기존 383 + 신규 15: `AdAutomationTest` 9 · `KarrotAdsClientTest` 6).
- **실제 PostgreSQL 16 에서 V1~V49 Flyway 적용 + Hibernate 스키마 검증 통과**, 암호화 키 없이도 정상 기동.
- **종단 테스트(실 Postgres + 가짜 당근 서버)**: 가입 → 당근 연결(틀린 키는 400 거절, 맞는 키만 저장·암호문 확인)
  → 캠페인 목록 → 규칙(하루 2건) → 공개 폼 접수 3건 → **2번째 접수 직후 pause 호출 정확히 1회**, 3번째엔 재발동 없음, 이력 기록.
- **장애 격리 실측**: 당근 서버 다운 / 응답 없이 매달림(10초 타임아웃) 상태에서도 **리드 접수 201 · 10~15ms**,
  다른 API 3ms — 실패는 실행 이력에 "연결하지 못했습니다" / "응답 시간이 초과됐습니다"로만 남았다.
- 관리 화면: tsc·oxlint·vite build 통과, Playwright(API 목업) 1280·375px 4개 탭·규칙 편집·안내 페이지 — 가로 넘침 0.
- ⚠️ **실제 당근 API 로는 아직 안 해봤다**(키 없음) — 배포 후 사용자 키로 확인 필요.

| **1차** | 공통 뼈대 + 당근 어댑터 + 일 수량 → 캠페인 끄기 + 수동 켜기/끄기 + 실행 이력·텔레그램 + 당근 안내 페이지 | ✅ 구현·검증(미배포) |
| 2차 | 메타 어댑터(시스템 사용자 토큰) + 메타 안내 페이지 + **시간대 조건(30분 단위)** | ⬜ |
| 3차 | 구글 어댑터(OAuth, REST) — 사용자 준비: 클라우드 프로젝트·Basic 접근·동의 화면 인증 | ⬜ |
| 이후 | 예산 증감 동작, 주 수량·CPA 조건, 성과(비용) 수집 → 매체별 리드 단가, 전환 반송(kmckid·gclid·fbclid) | ⬜ |

## 7. 매체 API 근거

- **당근**: [OpenAPI 가이드](https://businessdaangn.gitbook.io/business.daangn/ads-pro/tools/openapi) ·
  [레퍼런스](https://ads-openapi.kr.karrotmarket.com/)(Beta v0.7.0, 2026-11-13). 헤더 `X-API-KEY` + `X-ADVERTISER-ID`.
  `GET /v1/campaigns?pageNumber&pageSize`, `POST /v1/campaigns/{id}/pause|resume`. 한도 광고 관리 분당 60회(계정 단위, 초과 시 429).
  키는 광고계정마다 따로, **재발급하면 기존 키 즉시 폐기**, **전문가모드만**, 외부 솔루션 입력 공식 허용. 검색광고는 조회 전용.
- **메타**: 시스템 사용자 토큰(만료 없음) — 본인 비즈니스 소유 광고계정이면 앱 심사 불필요(제한 접근 등급).
  캠페인 `status=PAUSED|ACTIVE`. 레이트리밋 `X-Business-Use-Case-Usage`.
- **구글**: 2026-09-09 개발자 토큰 폐지 → 접근 등급이 Google Cloud 프로젝트에 붙음(Explorer 2,880/일, Basic 15,000/일).
  캠페인 `status` 를 `CampaignService` mutate(REST `customers/{id}/campaigns:mutate`).
