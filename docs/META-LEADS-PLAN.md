# docs/META-LEADS-PLAN.md — 메타 잠재고객 폼 → 리드팟 연동 (설계)

> **상태**: 설계만 (2026-08-05). **코드 미착수.**
> 방향은 **A안(구글시트 Apps Script push)** 으로 사용자가 확정했다.
> 착수 전 [MESSAGING-PLAN.md](MESSAGING-PLAN.md) §9·§11 과 이 문서의 "§4 반드시 처리할 것"을 반드시 재정독한다.

---

## 1. 무엇을 하려는 것인가

마케터가 **메타(페이스북·인스타그램) 잠재고객 캠페인**을 돌리면 접수가 구글 스프레드시트로 실시간 들어온다.
그 리드를 **리드팟 리드폼에 연결해**, 리드팟이 이미 갖고 있는 기능(문자 발송·텔레그램 알림·광고주 공유·통계)을
메타 리드에도 그대로 적용하는 것이 목표다.

사용자 아이디어(2026-08-05): *"잠재입력폼에서 받는 인풋값들과 동일한 리드폼을 만들어두고 그걸로 받는다.
일반 리드폼 말고 '잠재 연동 리드폼'이라는 걸 만들어 관리한다."*
→ **방향은 맞다.** 다만 구현 위치에 대한 지적은 §4-6 참고.

---

## 2. 경로 3가지와 선택

| 안 | 방식 | 실시간성 | 플랫폼 승인 | 난이도 |
|---|---|---|---|---|
| **A ✅ 확정** | 고객 시트에 **Apps Script** 설치 → 리드팟 인바운드 API 로 POST | **최소 1분** (§3) | 없음 | 낮음 |
| B | 리드팟 서버가 **Google Sheets API** 로 폴링 | 우리가 정함 | Google OAuth / 서비스계정 | 중간 |
| C | **메타 Lead Ads 웹훅** 직접 연동(시트 없이) | 수초 | `leads_retrieval` 앱 심사 + 비즈니스 인증 (수 주) | 높음 |

**A를 고른 이유**
1. 플랫폼 승인이 **필요 없다** — 우리 코드만으로 완결된다.
2. 우리가 이미 하는 아웃바운드(`settingsConfig.sheetsSpreadsheetId` → Sheets API)의 **역방향**이라 개념이 일관된다.
   (2026-08-11 이전에는 아웃바운드가 Apps Script 웹훅이었다 — 서비스 계정으로 교체됨.)
3. **나중에 C로 갈아끼울 때 인바운드 수신부를 그대로 재사용**한다 — 바뀌는 건 앞단(누가 POST 하는가)뿐이다.

**C는 언젠가 해야 한다.** 시트를 거치지 않아 지연이 수초고, 고객이 스크립트를 설치할 필요가 없다.
A를 먼저 만들어 인바운드 수신부·매핑·멱등성을 검증한 뒤 옮기는 순서가 맞다.

## 3. ⚠️ A안의 결정적 제약 — "실시간"이 아니다

**Apps Script 의 `onEdit`·`onChange` 트리거는 외부 서비스가 Sheets API 로 쓴 변경에 발동하지 않는다.**
Google 공식 문서 표현: *"Script executions and API requests don't cause triggers to run."*

메타 리드가 시트에 들어오는 경로는 (Zapier·Make·LeadsBridge 등 무엇을 쓰든) **결국 Sheets API 쓰기**다.
따라서 **시간 기반 트리거(time-driven, 최소 주기 1분)로 새 행을 스캔하는 방식밖에 없다.**

> 커뮤니티에는 "installable `onChange` 는 Sheets API 쓰기에도 발동한다"는 보고가 있는데
> **상충되는 보고가 함께 있어 의존해선 안 된다.** 설계는 시간 기반을 기준으로 하고,
> onChange 가 발동하면 지연이 줄어드는 **보너스**로만 취급한다.

**결과: 접수 → 리드팟 도착까지 최대 1분 지연.**
고객 응대 문자라면 대체로 괜찮지만, **"실시간"이라고 약속하면 안 된다.** 화면 문구에도 "최대 1분"으로 적는다.

## 4. 반드시 처리할 것 (하나라도 빠지면 사고가 난다)

### 4-1. 🔴 멱등성 (중복 차단) — 이걸 안 하면 돈이 샌다

시트를 **주기적으로 스캔**하는 구조라 같은 행을 두 번 읽을 수 있다(스크립트 재실행·마지막 처리 위치 유실·
시트 재정렬·고객이 행을 복사). 그러면 **리드가 두 건 생기고 문자가 두 번 나간다 = 비용 2배.**

- **행마다 고유키를 정해 저장하고, 이미 있으면 버린다.** 우선순위:
  1. 메타 `leadgen_id`(있으면 최선 — 메타가 부여하는 진짜 고유값)
  2. 없으면 `시트ID + 시트명 + 행번호`
  3. 그것도 불안하면 정규화된 답변 전체의 해시
- ⚠️ **기존 중복 방지(K3, `LeadService.checkDuplicates`)로는 부족하다.** 그건 "같은 연락처"를 막는 기능이라
  **진짜로 두 번 신청한 사람과 시스템 중복을 구분할 수 없다.** 별개의 장치가 필요하다.
- 저장 위치: `leads` 에 `external_id` 컬럼 + `(form_id, external_id)` 부분 유니크 인덱스가 유력.
  ⚠️ **유니크 인덱스를 쓸 때 V22 의 함정을 기억할 것** — 부분 유니크 인덱스는 `DEFERRABLE` 로 만들 수 없고,
  Hibernate 는 한 트랜잭션에서 INSERT 를 orphan DELETE 보다 먼저 실행한다(PROGRESS 2026-08-04 절 참고).

### 4-2. 🔴 동의 근거 (법적 리스크)

**메타 잠재고객 폼에는 우리 동의문서가 없다.** 그런데 리드팟은 접수자에게 문자를 보낼 수 있다.

- 상담 신청에 대한 **응답성 문자**와 **광고성 문자**는 요구되는 근거가 다르다.
- 메타 폼에는 **커스텀 질문(동의 체크)** 을 넣을 수 있다 → 그 값을 우리 `consents` 로 매핑해야 한다.
- **동의 값이 없는 리드에는 고객향 문자를 보내지 않는 것이 기본값**이어야 한다.
  (마케터·광고주 알림은 내부 수신자라 별개다 — MESSAGING-PLAN §9 원칙)
- ⚠️ **착수 전에 사용자와 정리해야 하는 항목이다.** 코드보다 이게 먼저다.

### 4-3. 🔴 `importRows` 는 문자를 보내지 않는다 — 이게 실제 핵심 난점

기존 일괄 등록([LeadService.java](../backend/src/main/java/com/leadpot/lead/LeadService.java) `importRows`)은
`leadRepository.save` 만 하고 **`notifyNewLead` 를 호출하지 않는다.** 즉 **그 경로로 넣으면 문자·텔레그램이 안 나간다.**
그런데 이 기능의 목적이 바로 "문자를 보내는 것"이다.

→ **`submit()` 경로를 타야 한다.** 그런데 submit 은 공개 폼 제출 전제로 설계돼 있어 그대로는 안 맞는다:

| submit 의 단계 | 외부 유입에서 어떻게 할지 |
|---|---|
| `checkIpBlocked` | 방문자 IP 가 **없다**(우리 서버로 직접 들어옴) → **건너뛴다** |
| `validate` (필수·형식) | **적용한다.** 단 메타 폼과 우리 폼 항목이 어긋나면 전부 실패하므로 매핑 검증이 먼저 |
| `checkDuplicates` (K3) | 적용 여부를 **정해야 한다** — 4-1 의 멱등성과 역할이 다르다 |
| `stampVarKeys` | **적용한다**(문자 템플릿이 varKey 로 값을 찾는다) |
| `notifyNewLead` | **적용한다** ← 이게 목적 |

→ 설계 선택: `submit()` 에 "유입 출처" 개념을 넣어 분기할지, `submitExternal()` 을 따로 둘지.
**전자를 권한다** — 후자는 알림 로직이 두 곳으로 갈라져 한쪽만 고치는 사고가 난다.

### 4-4. 인바운드 인증

시크릿 없이 열면 **아무나 우리 리드폼에 리드를 밀어넣을 수 있다**(문자까지 나간다).
- 리드폼별 시크릿을 발급하고 Apps Script 가 헤더/본문에 실어 보낸다.
- ~~우리는 아웃바운드에서 이미 `settingsConfig.sheetsSecret` 을 쓰고 있다~~ — **2026-08-11 삭제됨**.
  아웃바운드가 서비스 계정 방식이 되면서 공유 시크릿이 필요 없어졌다(구글이 인증한다).
  인바운드는 여전히 시크릿이 필요하다 — 여기서 처음 만들어야 한다.
- 시크릿 노출 시 **재발급**이 가능해야 한다.
- 요청량 제한(rate limit)도 필요하다 — 잘못 만든 스크립트가 1분마다 수천 행을 밀어넣을 수 있다.

### 4-5. 컬럼 매핑 UI

"동일한 리드폼을 미리 만들어둔다"는 발상이 매핑 문제를 **줄이지만 없애지는 못한다.**
메타 컬럼명은 질문 전문·영문 필드명·한글이 섞여 오고, 고객이 시트 헤더를 바꿀 수도 있다.
→ **시트 헤더 ↔ 리드폼 항목(varKey) 매핑을 저장하는 화면**이 필요하다. 매핑되지 않은 헤더는 눈에 보이게 남긴다.

### 4-6. '잠재 연동 리드폼'을 어디에 둘까 — `FormType` 이 아닐 수 있다

현재 `FormType`(BASIC/STEP)은 **렌더러 선택용**이다. 잠재 연동 폼은 성질이 다르다:
- **공개 렌더가 되면 안 된다.** 공개 URL 이 살아 있으면 아무나 제출할 수 있고, 그 제출은 메타 리드가 아니다.
- 빌더 화면에 필요한 것은 디자인 설정이 아니라 **매핑·시크릿·동의 설정**이다.

→ `FormType` 에 값을 추가하면 "렌더러가 없는 FormType" 이라는 예외가 생긴다.
**`Form` 에 유입 출처(예: `source = SELF | META_SHEET`)를 별도 필드로 두는 편이 깔끔하다.**
착수 시 확정한다.

### 4-7. 비용·권한 (선행 조건)

메타 리드는 **양이 많다.** 문자 단가가 붙으면 비용이 빠르게 커진다.
→ **[V25 계정별 문자 권한·월 한도](../backend/src/main/resources/db/migration/V25__sms_permissions.sql)가
먼저 배포·검증돼 있어야** 이 기능을 안전하게 열 수 있다. (2026-08-05 구현 완료, 배포 대기)

## 5. 흐름 (A안)

```
[메타 잠재고객 폼 제출]
   │
   ▼ (메타/재피어 등이 Sheets API 로 행 추가)
[고객의 구글 스프레드시트]
   │
   ▼ 시간 기반 트리거 (최소 1분) — ⚠️ onEdit/onChange 는 발동하지 않는다(§3)
[Apps Script] 마지막 처리 위치 이후의 새 행만 읽어 POST
   │  헤더: 리드폼 시크릿
   │  본문: { externalId, rows: [{헤더: 값, ...}] }
   ▼
[리드팟 인바운드 API]  (/api/public/... 또는 시크릿 기반 별도 경로)
   ├─ 시크릿 검증 (4-4)
   ├─ 멱등성 검사 — 이미 받은 externalId 면 버린다 (4-1)
   ├─ 헤더 → 항목(varKey) 매핑 (4-5)
   ├─ 동의 값 확인 — 없으면 고객향 문자 대상에서 제외 (4-2)
   └─ 리드 저장 + notifyNewLead (4-3)
        └─→ 문자 / 텔레그램 / 구글시트 / 광고주 알림
```

## 6. 단계별 작업 순서 (제안)

1. **동의 근거 정리** (4-2) — 코드보다 먼저. 사용자 결정 필요.
2. **`Form.source` + 매핑·시크릿 저장 구조** 확정 (4-6, 4-5)
3. **인바운드 수신 API** — 시크릿 검증 + 멱등성 + 매핑 (4-1, 4-4)
   → 이 단계는 C안으로 갈아탈 때도 **그대로 재사용**된다.
4. **`submit` 경로에 유입 출처 분기** (4-3)
5. **Apps Script 배포용 스크립트 + 설치 안내** (고객이 복붙할 수 있는 형태)
6. **매핑 화면**
7. 실측 검증 — 지연·중복·문자 발송

---

## 7. 착수 전 사용자에게 물을 것

1. **동의 근거** — 메타 폼에 동의 질문을 넣을 수 있는가? 넣기 전까지 고객향 문자를 막아둘까?
2. **최대 1분 지연**을 허용하는가? (허용 못 하면 C안 = 메타 앱 심사로 가야 한다)
3. **K3 중복 방지**를 외부 유입에도 적용할까? (같은 사람이 다른 캠페인으로 두 번 신청할 수 있다)
4. Apps Script 를 **고객이 직접 설치**하게 할지, 우리가 대신 설치해줄지 (운영 부담이 갈린다)
