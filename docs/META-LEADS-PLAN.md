## 1. 무엇을 하려는 것인가

마케터가 **메타(페이스북·인스타그램) 잠재고객 캠페인**을 돌리면 접수 즉시 리드팟으로 들어오게 한다.
그 리드를 **리드팟 리드폼에 연결해**, 리드팟이 이미 갖고 있는 기능(문자 발송·텔레그램 알림·광고주 공유·통계)을
메타 리드에도 그대로 적용하는 것이 목표다.

사용자 아이디어(2026-08-05): *"잠재입력폼에서 받는 인풋값들과 동일한 리드폼을 만들어두고 그걸로 받는다.
일반 리드폼 말고 '잠재 연동 리드폼'이라는 걸 만들어 관리한다."*
→ **방향은 맞다.** 다만 구현 위치에 대한 지적은 §4-6 참고.

## 2. 경로 — LeadsBridge 웹훅으로 확정 (2026-08-31)

| 안 | 방식 | 실시간성 | 플랫폼 승인 | 비용 |
|---|---|---|---|---|
| **LeadsBridge 웹훅 ✅ 확정** | LeadsBridge(메타 공식 기술 파트너)가 메타 리드를 받아 우리 웹훅 URL로 즉시 POST | **수초** | **불필요**(LeadsBridge 가 이미 `leads_retrieval` 승인 보유) | LeadsBridge 유료 구독 필요할 가능성 큼(§2-1) |
| A (2026-08-05 구 확정, 폐기) | 고객 시트에 Apps Script 설치 → 리드팟 인바운드 API 로 POST | 최대 1분 | 없음 | 무료 |
| B | 리드팟 서버가 Google Sheets API 로 폴링 | 우리가 정함 | Google OAuth | 무료 |
| C | 메타 Lead Ads 웹훅 **직접** 연동(중개자 없이) | 수초 | 우리가 직접 `leads_retrieval` 앱 심사 + 비즈니스 인증(수 주) | 무료(개발 비용만) |

**LeadsBridge 를 고른 이유** (사용자 확정)
1. C안의 유일한 장벽이었던 **메타 앱 심사·비즈니스 인증(수 주)** 을 우회한다 — LeadsBridge 가 이미 메타의
   공식 기술 파트너로 승인을 보유하고 있어, 우리는 심사 없이 웹훅만 받으면 된다.
2. A안의 **"최대 1분 지연" + "고객이 Apps Script 를 직접 설치해야 함"** 제약이 사라진다. 웹훅 기반이라 지연이 수초.
3. **수신부(§4) 설계는 그대로 재사용된다** — 보내는 쪽이 시트든 LeadsBridge든 메타 직접이든, 우리 인바운드 API 가
   해야 할 일(멱등성·인증·매핑·동의 확인·`submit()` 라우팅)은 동일하다. 나중에 C안(직접 연동)으로 갈아탈 때도
   바뀌는 건 "누가 우리 웹훅을 호출하는가"뿐이다.

### 2-1. ⚠️ LeadsBridge 비용 — "무료"가 아닐 가능성이 큼, 가입 전 재확인 필수

2026-08-31 리서치(leadsbridge.com 은 이 환경의 egress 프록시가 막고 있어 **3rd-party 리뷰 사이트 경유로만

| 플랜 | 월 리드 한도 | 동기화 필드 수 | Bridge(연동) 수 | 가격(추정) | 웹훅 데스티네이션 |
|---|---|---|---|---|---|
| Free (forever) | 50건 | **2개** | 1개 | 무료 | 불명확 — 리뷰 사이트 기준 **미포함 가능성** |
| Starter | 800건 | 4개 | 3개 | 약 $22/월 | 불명확 |
| **Pro** | 2,000건 | 40개 | 15개 | 약 $60~79/월(연간 결제 기준) | **포함** (리뷰 사이트 기준) |
| Business | 맞춤 | 맞춤 | 맞춤 | 맞춤(영업 문의) | 포함 |

- 메타 잠재고객 폼은 보통 이름·연락처 외에 커스텀 질문(관심분야·동의 등)까지 **4개 이상** 필드를 받으므로,
  Free 의 "필드 2개까지"는 실사용에 부족할 가능성이 높다.
  **우리가 원하는 "커스텀 URL 로 웹훅 전송" 기능 자체가 Pro 플랜부터 열리는 것으로 보인다** — 즉 사실상
  **월 $60~79 선 유료 구독이 전제**일 수 있다. **가입 화면에서 웹훅 옵션 노출 여부를 직접 확인 후 진행할 것.**
- 리드 건수가 많아지면(메타 캠페인 특성상 빠르게 늘어남) 상위 플랜(Business)으로 올라갈 수 있음도 감안.
- 구독료 부담 주체·설정 주체는 §2-2 참고.

### 2-2. 사용 주체 — "광고주"가 아니라 마케터(리드팟 계정 소유자) 본인이 직접 설정

2026-08-31 사용자 확정: **메타 폼 ↔ 리드팟 리드폼 연결(Bridge 생성·필드 매핑)은 전부 마케터(캠페인을 직접 돌리는
리드팟 사용자)의 영역**이다. 이 기능은 "광고주별로 우리가 대신 세팅해주는 온보딩형 기능"이 아니라, **마케터가
빌더 화면에서 셀프서비스로 설정하는 기능**으로 만든다. (§4-6 의 매핑·시크릿 UI 는 이 전제로 설계한다.)

## 3. LeadsBridge 웹훅의 특성 (구 §3 "A안의 1분 지연 제약"을 대체)

- LeadsBridge → 우리 URL 로 **HTTP POST**(설정에 따라 GET 도 가능하나 POST 권장). **Content-Type: application/json**,
  **원본 필드를 그대로(pass-through) 전달**한다 — 즉 메타 폼의 질문 라벨/키를 LeadsBridge 가 임의로 바꾸지 않는다.
- 인증은 **Access Secret**(LeadsBridge 쪽 "Webhook" 연동 설정 화면에서 입력하는 시크릿 필드) 로 한다 — 우리가
  리드폼별로 발급한 시크릿을 여기 넣게 한다(§4-4).
- 지연은 메타 → LeadsBridge → 우리, 두 홉이지만 **웹훅 체인이라 수초~수십초 내외**로 기대한다(정확한 SLA는
  LeadsBridge 문서에 없음 — 실측 필요, §6-7).
- 재시도(retry) 정책은 LeadsBridge 문서에서 확인 필요 — **같은 리드가 두 번 올 수 있다고 가정**하고 멱등성을
  설계한다(§4-1, 원래도 필수였음).
- 페이로드에 메타의 `leadgen_id` 가 그대로 포함되는지는 **착수 시 실제 연동해서 확인**해야 한다(안 오면 §4-1 의
  차선책 사용).

## 4. 반드시 처리할 것 (하나라도 빠지면 사고가 난다)

### 4-1. 🔴 멱등성 (중복 차단) — 이걸 안 하면 돈이 샌다

LeadsBridge 도 웹훅 재시도가 있을 수 있고, 마케터가 같은 Bridge 를 재실행/재연결할 수도 있다. 그러면 **리드가
두 건 생기고 문자가 두 번 나간다 = 비용 2배.**

- **요청마다 고유키를 정해 저장하고, 이미 있으면 버린다.** 우선순위:
  1. 메타 `leadgen_id`(있으면 최선 — 메타가 부여하는 진짜 고유값, LeadsBridge 가 pass-through 하는지 착수 시 확인)
  2. 없으면 LeadsBridge 가 자체 부여하는 리드/제출 ID
  3. 그것도 없으면 정규화된 답변 전체의 해시
- ⚠️ **기존 중복 방지(K3, `LeadService.checkDuplicates`)로는 부족하다.** 그건 "같은 연락처"를 막는 기능이라
  **진짜로 두 번 신청한 사람과 시스템 중복(같은 리드가 재전송됨)을 구분할 수 없다.** 별개의 장치가 필요하다.
- 저장 위치: `leads` 에 `external_id` 컬럼 + `(form_id, external_id)` 부분 유니크 인덱스가 유력.
  ⚠️ **유니크 인덱스를 쓸 때 V22 의 함정을 기억할 것** — 부분 유니크 인덱스는 `DEFERRABLE` 로 만들 수 없고,
  Hibernate 는 한 트랜잭션에서 INSERT 를 orphan DELETE 보다 먼저 실행한다(PROGRESS 2026-08-04 절 참고).
- K3(같은 연락처 중복 방지)를 외부 유입에도 적용할지는 **아직 사용자 답 없음** — 기본값으로 "일반 제출과 동일하게
  K3 도 적용"을 추천한다(같은 사람이 여러 캠페인으로 두 번 신청하는 걸 막는 기존 정책과 일관됨). 착수 직전 재확인.

### 4-2. 🟡 동의 근거 — 메타 폼의 필수 질문으로 확보 (2026-08-31 확정)

2026-08-31 사용자 확정: **메타 잠재고객 폼에서 동의 질문을 필수(required)로 걸면, 동의하지 않은 방문자는애초에
폼 제출 자체가 안 되므로** 우리에게 도달하는 리드는 이미 동의된 상태다. 즉 "동의 없는 리드에 문자를 보낼지 말지"
고민은 **메타 폼 설계(마케터의 몫)로 해결**한다 — 이 부분은 4-6 의 매핑 화면에서 마케터가 메타의 동의 질문을
우리 `consents` 항목에 매핑하면 된다.

- 그래도 **서버 쪽 안전장치는 유지**한다(비용이 거의 안 드는 방어적 기본값): 매핑된 동의 값이 비어 있는 리드가
  들어오면(마케터가 매핑을 빼먹었거나 메타 폼에 필수로 안 걸었을 경우) **고객향 문자는 기본적으로 보류**하고
  화면에 "동의 미확인" 표시만 한다. 마케터·광고주 알림은 내부 수신자라 별개(MESSAGING-PLAN §9 원칙).
- 광고성 문자(마케팅성)와 응답성 문자(상담 안내)는 요구 근거가 다를 수 있다는 점은 여전히 유효 — 메타 커스텀
  질문을 어떤 동의 항목(필수 상담동의 vs 광고성 수신동의)에 매핑할지는 마케터가 화면에서 정하게 한다.

### 4-3. 🔴 `importRows` 는 문자를 보내지 않는다 — 이게 실제 핵심 난점

기존 일괄 등록([LeadService.java](../backend/src/main/java/com/leadpot/lead/LeadService.java) `importRows`)은
`leadRepository.save` 만 하고 **`notifyNewLead` 를 호출하지 않는다.** 즉 **그 경로로 넣으면 문자·텔레그램이 안 나간다.**
그런데 이 기능의 목적이 바로 "문자를 보내는 것"이다.

→ **`submit()` 경로를 타야 한다.** 그런데 submit 은 공개 폼 제출 전제로 설계돼 있어 그대로는 안 맞는다
(2026-08-31 기준 `LeadService.submit()` 실제 코드 재확인 완료 — 아래 표 유효):

| submit 의 단계 | 외부 유입에서 어떻게 할지 |
|---|---|
| `checkIpBlocked` | 방문자 IP 가 **없다**(LeadsBridge 서버에서 직접 들어옴) → **건너뛴다** |
| `validate` (필수·형식) | **적용한다.** 단 메타 폼과 우리 폼 항목이 어긋나면 전부 실패하므로 매핑 검증이 먼저 |
| `checkDuplicates` (K3) | 적용 여부를 **정해야 한다** — 4-1 참고, 기본값 "적용" 추천 |
| `stampVarKeys` | **적용한다**(문자 템플릿이 varKey 로 값을 찾는다) |
| `notifyNewLead` | **적용한다** ← 이게 목적 |

→ 설계 선택: `submit()` 에 "유입 출처" 개념을 넣어 분기할지, `submitExternal()` 을 따로 둘지.
**전자를 권한다** — 후자는 알림 로직이 두 곳으로 갈라져 한쪽만 고치는 사고가 난다.

### 4-4. 인바운드 인증

시크릿 없이 열면 **아무나 우리 리드폼에 리드를 밀어넣을 수 있다**(문자까지 나간다).
- 리드폼별 시크릿을 발급하고, 마케터가 그 값을 **LeadsBridge 의 "Webhook" 연동 설정 화면의 Access Secret 필드**에
  입력한다(§3).
- 시크릿 노출 시 **재발급**이 가능해야 한다.
- 요청량 제한(rate limit)도 필요하다 — 설정 실수나 LeadsBridge 쪽 재시도 폭주에 대비.

### 4-5. 컬럼 매핑 UI

메타 질문 라벨(전문·영문 필드명·한글 혼재)과 우리 리드폼 항목(varKey)이 이름까지 완전히 같으리라는 보장은 없다.
→ **LeadsBridge 가 보낸 JSON 키 ↔ 리드폼 항목(varKey) 매핑을 저장하는 화면**이 필요하다(마케터가 셀프서비스로
설정, §2-2). 매핑되지 않은 키는 눈에 보이게 남긴다. 첫 웹훅 수신 시 실제로 온 키 목록을 보여주면 매핑이 쉬워진다
("샘플 페이로드 기반 매핑 도우미").

### 4-6. '잠재 연동 리드폼'을 어디에 둘까 — `FormType` 이 아닐 수 있다

현재 `FormType`(BASIC/STEP)은 **렌더러 선택용**이다(2026-08-31 `Form.java` 재확인 — `formType` 필드 외
`source` 류 필드는 아직 없음, 코드 미착수 상태 그대로). 잠재 연동 폼은 성질이 다르다:
- **공개 렌더가 되면 안 된다.** 공개 URL 이 살아 있으면 아무나 제출할 수 있고, 그 제출은 메타 리드가 아니다.
- 빌더 화면에 필요한 것은 디자인 설정이 아니라 **매핑·시크릿·동의 매핑 설정**(마케터 셀프서비스, §2-2).

→ `FormType` 에 값을 추가하면 "렌더러가 없는 FormType" 이라는 예외가 생긴다.
**`Form` 에 유입 출처(예: `source = SELF | META_LEADSBRIDGE`)를 별도 필드로 두는 편이 깔끔하다.**
착수 시 확정한다(향후 LeadsBridge 아닌 다른 경로를 또 추가할 수 있으니 값 이름은 확장 가능하게).

### 4-7. 비용·권한 (선행 조건)

메타 리드는 **양이 많다.** 문자 단가가 붙으면 비용이 빠르게 커진다.
→ **[V25 계정별 문자 권한·월 한도](../backend/src/main/resources/db/migration/V25__sms_permissions.sql)가
먼저 배포·검증돼 있어야** 이 기능을 안전하게 열 수 있다. (2026-08-05 구현 완료 — 2026-08-31 기준 마이그레이션이
V38 까지 진행돼 있어 V25 는 이미 반영·운영 중으로 보임, 착수 시 실배포 상태만 재확인.)

```
[메타 잠재고객 폼 제출]
   │
   ▼ (메타 → LeadsBridge, 파트너 승인 경로라 지연 거의 없음)
[LeadsBridge] "Webhook" 데스티네이션(마케터가 리드팟 웹훅 URL + Access Secret 등록, §2-2)
   │  HTTP POST, JSON, 원본 필드 pass-through
   ▼
[리드팟 인바운드 API]  (예: POST /api/public/leadsbridge/{formId} 또는 시크릿 기반 별도 경로)
   ├─ 시크릿 검증 (4-4)
   ├─ 멱등성 검사 — 이미 받은 external_id 면 버린다 (4-1)
   ├─ 페이로드 키 → 항목(varKey) 매핑 (4-5)

   └─ `submit()` 경로로 리드 저장 + notifyNewLead (4-3)
        └─→ 문자 / 텔레그램 / 구글시트 / 광고주 알림
```

## 6. 단계별 작업 순서 (제안, 갱신)

1. **LeadsBridge 요금제·웹훅 데스티네이션 실제 확인** (§2-1) — 가입 화면에서 Pro 이상만 웹훅이 열리는지,
   가입 없이도 문서로 확인 가능한지 먼저 본다. **사업 비용 판단이 필요하면 착수 전 사용자에게 재확인.**
2. **`Form.source` + 매핑·시크릿 저장 구조** 확정 (4-6, 4-5)
3. **인바운드 수신 API** — 시크릿 검증 + 멱등성 + 매핑 (4-1, 4-4)
   → 이 단계는 나중에 다른 경로(C안 등)로 갈아탈 때도 **그대로 재사용**된다.
4. **`submit` 경로에 유입 출처 분기** (4-3)
5. **매핑 화면**(마케터 셀프서비스, 첫 웹훅 페이로드로 매핑 도우미) + **LeadsBridge 설정 가이드 문서**

6. K3 중복 방지 적용 여부 최종 확정(§4-1) 후 반영
7. 실측 검증 — 지연·중복·문자 발송·실제 메타 캠페인 1개로 종단 테스트

## 10. 실제 구현 요약 (2026-08-31, V39) — 벤더 무관 범용 웹훅으로 구현됨

§2-2 에서 방향을 "특정 벤더 종속 없는 범용 인바운드 웹훅"으로 최종 일반화한 뒤 바로 구현했다. 아래는
실제로 붙은 것 — 이후 세션은 여기부터 이어가면 된다(설계 논의였던 §1~§9 는 경위 기록으로 남긴다).

### 스키마 (`V39__inbound_webhook_leads.sql`)
- `forms.source`(SELF|WEBHOOK, 기본 SELF) — WEBHOOK 이면 공개 렌더(`/f/{id}`)가 막힌다(`FormService.getPublic`).
- `forms.webhook_token_hash` — 토큰 원문은 저장 안 함(SHA-256 해시만, `WebhookTokens` — `InviteTokens` 와 동일 원칙).
- `forms.webhook_config`(JSONB) — `answerMapping`/`consentMapping`(원본 키→라벨/제목) · `externalIdKey` ·
  `lastPayload`/`lastReceivedAt`(매핑 화면 도우미) · `lastError`/`lastErrorAt`.
- `leads.external_id` + `(form_id, external_id)` 부분 유니크 인덱스 — 멱재성(4-1) DB 최종 방어선.

### 백엔드
- **관리 API**(로그인, 본인 폼만): `GET/POST/DELETE /api/forms/{id}/webhook`, `POST .../regenerate`,
  `PUT .../mapping` — `WebhookLeadConfigController` → `FormService` (토큰은 활성화/재발급 응답에서 원문이
  **한 번만** 내려간다, 이후엔 해시만 남아 다시 보여줄 수 없다 — 잊으면 재발급).
  ⚠️ `source` 는 **`FormRequest`(일반 저장 API)에 없다** — 웹훅 전용 API로만 바뀐다. 넣었으면 다른 설정을
  저장할 때마다(디자인·문구 수정 등) `null` 이 실려와 활성화된 웹훅이 조용히 꺼지는 사고가 났을 것.
- **공개 수신 API**: `POST /api/public/webhook-leads/{token}` (`PublicWebhookLeadController` →
  `WebhookLeadService`, `com.leadpot.lead.webhook` 패키지). 흐름: 토큰 해시로 폼 조회(없으면 404) →
  요청량 제한(`WebhookRateLimiter`, 폼별 분당 120건, 메모리 슬라이딩 윈도 — Railway 단일 인스턴스 전제) →
  멱등성 키 계산(매핑된 키 우선, 없으면 페이로드 정규화 해시 폴백) → 이미 받은 키면 조용히 버림(200,
  `created:false`) → 매핑으로 answers/consents 구성 → `LeadService.submit(req, visitor, external=true)` →
  성공/실패 모두 `webhook_config` 에 최근 수신 이력 기록(마케터가 리드폼 화면에서 바로 확인).
  **업무 검증 실패(필수 누락·동의 미확인)는 200 으로 응답**(발신자 재시도 폭풍 방지, 대신 화면에 오류 노출) —
  토큰 오류만 404, 과다요청만 429.
- **`LeadService.submit` 확장**: `submit(req, visitor, external)` — `external=true` 면 IP 차단(K2)만 건너뛴다.
  나머지(필수·형식·K3 중복·동의)는 공개 제출과 동일 — **K3 는 기본 적용으로 확정**(4-1 의 미결 질문, 별다른
  반론 없어 문서의 추천대로 감).  `Form.source` 와 `external` 플래그가 어긋나면(WEBHOOK 폼을 공개 경로로,
  또는 SELF 폼을 웹훅 경로로) 즉시 거부 — 공개 렌더 차단(getPublic)의 2차 방어선.
- 동의(4-2) 구현: `LeadService.validate` 는 "제출된 동의 배열"만 검사하므로, 웹훅 쪽에서 **폼의 동의 항목
  전부**를 순회해 매핑 안 된 항목도 `agreed:false` 로 채운다 — 그래야 필수 동의 미확인 시 진짜로 저장을
  막는다(사용자 확정: "동의 안 하면 접수 자체가 안 됨"을 그대로 구현, 별도의 "저장은 하되 문자만 보류"
  분기는 만들지 않았다 — 단순함 우선).

### 프론트
