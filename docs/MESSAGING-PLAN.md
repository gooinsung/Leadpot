# docs/MESSAGING-PLAN.md — 템플릿 기반 자동 발송 (문자·메일·알림톡)

> **상태**: 계획 확정 · **구현 예정(2026-08-02~)**. 착수 전 이 문서를 다시 읽고 [CLAUDE.md](../CLAUDE.md) §0 절차를 따른다.
> 진행상황 정본은 [PROGRESS.md](PROGRESS.md). 사전조사(비용·준비물)는 [BACKLOG.md](BACKLOG.md) H3.

## 1. 무엇을 만드는가

리드가 접수되면, **리드폼 항목값을 변수로 끼운 메시지**를 문자·메일(추후 알림톡)로 자동 발송한다.

### 대표 예시 (이 문서의 기준 시나리오)

리드폼 `개인회생 상담` 의 항목:

| 항목 | 변수키(내부) | 화면 표기 |
|---|---|---|
| 이름 | `f1` | `{이름}` |
| 연락처 | `f2` | `{연락처}` |
| 채무금액 | `f3` | `{채무금액}` |
| 문의사항 | `f4` | `{문의사항}` |

**템플릿(문자)** — 편집기에서는 항목명으로 보이고 저장은 변수키로 된다.

```
{이름} 님.
접수해주신 '{문의사항}'의 답변을 준비중입니다.
채무가 {채무금액}으로 확인됩니다.
빠르게 확인하여 전화 드리겠습니다.
명함 첨부드리니 명함 내번호로 오는 전화를 꼭 받아주세요
[명함.jpg 첨부]
```

**발송 규칙**: 트리거=리드 접수 직후 / 수신자=**리드 본인, 번호는 `{연락처}` 항목에서** / 채널=문자

**리드 접수**
```
이름: 홍길동 · 연락처: 010-1111-2222 · 채무금액: 3000만원
문의사항: 개인회생 어떻게 하나요?
```

**→ `010-1111-2222` 로 발송**
```
홍길동 님.
접수해주신 '개인회생 어떻게 하나요?'의 답변을 준비중입니다.
채무가 3000만원으로 확인됩니다.
빠르게 확인하여 전화 드리겠습니다.
명함 첨부드리니 명함 내번호로 오는 전화를 꼭 받아주세요
```

동시에 별도 규칙으로 **마케터·광고주에게** 새 리드 알림 메일이 나갈 수 있다.

## 2. 확정된 결정 (2026-08-01 사용자)

| 항목 | 결정 | 비고 |
|---|---|---|
| **1단계 채널** | **문자 · 메일** | 알림톡은 사용자가 카카오 심사 접수 예정 → 승인 후 연결 |
| **변수 기준** | **항목에 변하지 않는 변수키 부여** | `FormBlock.id` 는 쓸 수 없다(§5 참고) |
| **변수 표기** | 편집기에는 **항목명**, 저장은 **변수키** | 항목명을 바꿔도 템플릿이 안 깨지고 표시만 따라 바뀐다 |
| **수신자 — 리드 본인** | 템플릿·규칙에서 **어느 항목을 수신 번호/메일로 쓸지 지정** | 연락처·이메일 항목이 없는 리드폼은 이 규칙을 만들 수 없게 막는다 |
| **수신자 — 마케터·광고주** | 계정에 등록된 연락처·이메일 사용 | |
| **메일 발신** | **우리 도메인으로 발신 + `Reply-To` 를 담당자로** | 마케터는 준비 없이 즉시 사용, 스팸함에 안 빠진다 |
| **문자 발신** | **마케터가 자기 문자 계정(솔라피 등)을 연동** | 발신번호 사전등록·명의 서류는 마케터 몫. 우리가 대표 발송하면 마케터들 명의서류를 모아야 해 비현실적 |
| **발신 프로필** | **리드폼별 지정** | 리드폼을 담당자별로 만들면 사실상 담당자별 발신이 된다 |
| **트리거** | ① 리드 접수 직후(필수) ② 리드 상태 변경 ③ 리드 골라서 수동 발송 | **지연·예약 발송은 제외**(스케줄러 필요, 나중) |
| **안전장치** | **리드폼을 수정하면 그 리드폼의 발송 규칙을 자동으로 끈다** | 항목이 바뀌어 변수가 깨진 채로 발송되는 사고 방지. ⚠️ §7 열린 질문 참고 |

## 3. 데이터 모델 (제안)

**다음 Flyway 는 V22.**

```
message_templates                    -- 템플릿
  id, user_id, name, channel(SMS|EMAIL|ALIMTALK)
  subject            -- 메일 제목(문자는 null)
  body               -- 변수키가 박힌 본문. 예: "{{f1}} 님. ..."
  attachments        -- jsonb: [{name, url, size}]  (R2 업로드 재사용)
  alimtalk_template_code  -- 알림톡용 카카오 심사 번호(1단계는 null)
  created_at, updated_at

message_rules                        -- 발송 규칙
  id, user_id, form_id
  trigger_type(ON_SUBMIT|ON_STATUS_CHANGE|MANUAL)
  trigger_status     -- ON_STATUS_CHANGE 일 때 어떤 상태로 바뀔 때인지
  recipient_type(LEAD|MARKETER|ADVERTISER)
  recipient_var_key  -- recipient_type=LEAD 일 때 수신 번호/메일을 담은 항목의 변수키
  template_id
  enabled            -- 리드폼 수정 시 자동으로 false
  disabled_reason    -- 왜 꺼졌는지(사용자에게 알려주기 위해)
  created_at

message_logs                         -- 발송 이력
  id, user_id, form_id, lead_id, rule_id, template_id
  channel, recipient(마스킹 저장), rendered_body
  status(SENT|FAILED|SKIPPED), error, provider_message_id
  cost                -- 대행사가 알려주면 저장(정산·확인용)
  created_at

form_blocks.var_key                  -- 항목별 불변 변수키 (신규 컬럼)
```

- **리드 답변에 변수키 함께 저장**: 지금 `leads.answers` 는 `{label, value, fieldType}` 인데 `varKey` 를 추가한다. **신규 리드부터** 정확히 매칭되고, 과거 리드는 `label` 폴백으로 처리한다.
- **문자 계정 연동**: `integration_settings` 에 대행사 종류·API 키·발신번호 목록 추가(계정당 1행 구조 유지).
- **발신 프로필**: `form.settingsConfig` 에 `senderPhone` · `senderEmailName` · `replyTo` (마이그레이션 불필요).

## 4. 변수 시스템

1. **변수키 부여** — 항목을 만들 때 `f1`, `f2`, … 를 한 번 부여하고 **이후 절대 바꾸지 않는다. 항목을 지워도 그 키는 재사용하지 않는다**(지운 항목의 키를 새 항목이 물려받으면 과거 리드·템플릿이 엉뚱한 값을 가리킨다).
2. **편집기** — 변수 목록에서 클릭해 삽입한다. 화면에는 `{이름}`, 저장은 `{{f1}}`.
3. **렌더링** — `리드.answers` 에서 `varKey` 로 값을 찾는다. 없으면 `label` 로 폴백.
4. **값이 빈 경우** — 빈 문자열로 치환하고 **로그에 남긴다**. 필수 변수(수신 번호)가 비면 **발송하지 않고 SKIPPED** 로 기록한다.
5. **시스템 변수도 제공** — `{{form.name}}` · `{{lead.createdAt}}` · `{{marketer.name}}` 등.

## 5. ⚠️ 먼저 고쳐야 하는 기존 구조 (조사 결과)

착수 전에 이걸 모르면 설계가 무너진다.

**① `FormBlock.id` 는 안정적이지 않다 — 변수 기준으로 쓸 수 없다**
```java
@OneToMany(..., orphanRemoval = true)          // Form.java
public void replaceBlocks(...) { blocks.clear(); ... }
FormBlock b = new FormBlock();                 // FormBlockDto.toEntity() — id 를 넘기지 않는다
```
리드폼을 한 번 저장하면 **항목이 전부 삭제되고 새 ID 로 재생성**된다. 그래서 숫자 ID 를 템플릿에 박으면 리드폼을 한 번만 수정해도 전부 깨진다(항목명보다 더 위험). → **별도 `var_key` 를 두는 이유.**

**② 리드 답변이 항목명(label)으로만 저장된다**
```json
"answers": [ { "label": "이름", "value": "홍길동", "fieldType": "text" } ]
```
항목 ID·키가 없다. → **`varKey` 를 answers 에 추가**해야 항목명을 바꿔도 과거 리드가 살아난다.

## 6. 단계별 작업 순서 (제안)

| 단계 | 내용 | 비고 |
|---|---|---|
| **M1** | `form_blocks.var_key` 추가 + 기존 항목 백필 + 저장 시 유지 · `leads.answers` 에 `varKey` 기록 | **다른 모든 단계의 전제**. 여기가 틀리면 뒤가 다 흔들린다 |
| **M2** | 템플릿 CRUD + 편집기(변수 삽입·미리보기) | 미리보기는 실제 리드 하나를 골라 렌더해서 보여준다 |
| **M3** | **메일 발송** (우리 도메인 + Reply-To) | 사업자등록 불필요·거의 무료 → 가장 먼저 실제로 돌려볼 수 있다 |
| **M4** | 발송 규칙 + 트리거(접수 직후·상태 변경) + 발송 로그 화면 | `NotificationService.planDispatches()` 구조를 확장해 붙인다 |
| **M5** | **문자 발송** (마케터 계정 연동, 발신번호 선택) | 대행사 어댑터를 인터페이스로 두고 솔라피부터 |
| **M6** | 수동 발송(리드 골라서) · 첨부파일 | BACKLOG F5 와 연결 |
| **M7** | 알림톡 — 카카오 심사 통과 후 `templateCode` 매핑 | 심사된 본문과 우리 템플릿이 일치하는지 검사 필요 |

## 7. 열린 질문 (착수 전 사용자 확인)

- [ ] **"리드를 수정하는 경우 자동으로 끈다"의 대상** — 현재 **리드 답변을 수정하는 기능은 없다**(상태변경·태그·메모만). 그래서 **리드폼 수정**으로 해석해 §2 에 적었다. 만약 앞으로 리드 답변 수정 기능을 만들 계획이고 "그때 발송이 다시 나가면 안 된다"는 뜻이었다면 규칙이 달라진다.
- [ ] **자동으로 끈 뒤 어떻게 알릴지** — 리드폼을 저장하면 규칙이 조용히 꺼지면 마케터가 모른다. 저장 시 경고 + 규칙 화면에 "꺼짐(리드폼이 수정됨)" 표시 + 다시 켜기 버튼을 두는 것을 제안한다.
- [ ] **같은 리드에 중복 발송 방지** — 상태를 여러 번 오가면(상담중→신규→상담중) 같은 메시지가 반복 발송된다. 규칙별로 **리드당 1회만** 을 기본값으로 할지.
- [ ] **실패 재시도** — 대행사 순간 오류로 유실되면 곤란하다. 지수 백오프 2~3회를 넣을지(현재 웹훅에는 재시도가 없다).
- [ ] **수신거부** — 정보성(접수 확인)은 동의 없이 가능하지만, 마케팅성 발송을 하려면 수신거부 처리와 광고성 수신동의 연결이 필요하다.

## 8. 참고 — 이미 있어서 재사용할 것

- **`NotificationService.planDispatches()`** — 발송 대상을 목록화한 뒤 채널별로 보내는 구조가 이미 있다(텔레그램·웹훅). **채널을 추가하는 형태**로 들어간다.
- **`notification_logs`** — 발송 성공/실패 기록 패턴이 이미 있다.
- **커밋 후 비동기 발송** — 리드 접수 트랜잭션이 커밋된 뒤에만 발송하는 장치가 이미 있다(롤백 시 발송 안 됨).
- **리드폼별 on/off 토글** — `settingsConfig.notifyEnabled` 패턴.
- **R2 파일 업로드** — 명함 등 첨부파일 저장에 재사용(`landing-image/YYYY/MM/DD/` 규칙 참고).
- **⚠️ 웹훅으로 이미 가능한 것** — `sendSheets()` 는 도메인 제한이 없어 **Make·Zapier Webhook URL 을 넣으면 그대로 동작한다**(리드폼 편집 > 구글시트 웹훅 칸). 급하면 그쪽으로 문자·메일을 우회 발송할 수 있다. 단 리드폼당 1개만·재시도 없음·`new_lead` 이벤트만.
