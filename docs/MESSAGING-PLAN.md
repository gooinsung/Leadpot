## 1. 무엇을 만드는가

리드가 접수되면, **리드폼 항목값을 변수로 끼운 메시지**를 문자·메일(추후 알림톡)로 자동 발송한다.

### 대표 예시 (이 문서의 기준 시나리오)

리드폼 `개인회생 상담` 의 항목:

| 항목 | 변수키(내부) | 화면 표기 |
|---|---|---|
| 이름 | `f1` | `{이름}` |
| 연락처 | `f2` | `{연락처}` |
| 채무금액 | `f3` | `{채무금액}` |
| 문의사항 | `f4` | `{문의사항}` |

**템플릿(문자)** — 편집기에서는 항목명으로 보이고 저장은 변수키로 된다.

```
{이름} 님.
접수해주신 '{문의사항}'의 답변을 준비중입니다.
채무가 {채무금액}으로 확인됩니다.
빠르게 확인하여 전화 드리겠습니다.
명함 첨부드리니 명함 내번호로 오는 전화를 꼭 받아주세요
[명함.jpg 첨부]
```

**발송 규칙**: 트리거=리드 접수 직후 / 수신자=**리드 본인, 번호는 `{연락처}` 항목에서** / 채널=문자

**리드 접수**
```
이름: 홍길동 · 연락처: 010-1111-2222 · 채무금액: 3000만원
문의사항: 개인회생 어떻게 하나요?
```

**→ `010-1111-2222` 로 발송**
```
홍길동 님.
접수해주신 '개인회생 어떻게 하나요?'의 답변을 준비중입니다.
채무가 3000만원으로 확인됩니다.
빠르게 확인하여 전화 드리겠습니다.
명함 첨부드리니 명함 내번호로 오는 전화를 꼭 받아주세요
```

동시에 별도 규칙으로 **마케터·광고주에게** 새 리드 알림이 나갈 수 있다(메일 또는 **알림톡**).

> **채널별 역할이 다르다** (2026-08-01 사용자 확정)
> - **리드 본인**에게 가는 상세 내용(명함·채무금액·문의사항 회신) → **문자**
> - **마케터·광고주**에게 가는 "리드폼이 접수되었습니다" 알림 → **알림톡** (상세는 §9)

## 2. 확정된 결정 (2026-08-01 사용자)

| 항목 | 결정 | 비고 |
|---|---|---|
| **1단계 채널** | **문자 · 메일** | 알림톡은 사용자가 카카오 심사 접수 예정 → 승인 후 연결 |
| **알림톡 용도** | **마케터·광고주에게 "리드폼이 접수되었습니다" 알림만** | 리드 본인용 상세(명함·채무금액)는 문자. 상세 §9 |
| **변수 기준** | **항목에 변하지 않는 변수키 부여** | `FormBlock.id` 는 쓸 수 없다(§5 참고) |
| **변수 표기** | 편집기에는 **항목명**, 저장은 **변수키** | 항목명을 바꿔도 템플릿이 안 깨지고 표시만 따라 바뀐다 |
| **수신자 — 리드 본인** | 템플릿·규칙에서 **어느 항목을 수신 번호/메일로 쓸지 지정** | 연락처·이메일 항목이 없는 리드폼은 이 규칙을 만들 수 없게 막는다 |
| **수신자 — 마케터·광고주** | 계정에 등록된 연락처·이메일 사용 | |
| **메일 발신** | **우리 도메인으로 발신 + `Reply-To` 를 담당자로** | 마케터는 준비 없이 즉시 사용, 스팸함에 안 빠진다 |
| **문자 발신** | ~~마케터가 자기 문자 계정을 연동~~ → **리드팟 계정(우리 API 키) 하나로만 발송** | 2026-08-01 변경 → 08-02 마케터 자기 키 경로 제거(V24). 상세·발신번호 제약은 §11 |
| **발신 프로필** | **리드폼별 지정** | 리드폼을 담당자별로 만들면 사실상 담당자별 발신이 된다 |
| **트리거** | ① 리드 접수 직후(필수) ② 리드 상태 변경 ③ 리드 골라서 수동 발송 | **지연·예약 발송은 제외**(스케줄러 필요, 나중) |
| **안전장치** | **템플릿이 쓰는 변수키가 사라졌을 때만** 그 리드폼의 발송 규칙을 끈다 | 대상은 **리드폼** 수정(리드 답변 수정 기능은 없다). 저장 전후 `var_key` 집합을 비교 → 항목 추가·삭제로 템플릿 변수가 깨지면 끈다. **항목명·placeholder·옵션만 바뀐 경우는 유지**(무조건 끄면 사소한 수정에도 발송이 조용히 멈춘다) |
| **메일 서비스** | **Resend** | 월 3,000건 무료·API 단순·도메인 인증 자동화. M3 에서 사용 |
| **중복 발송** | **규칙별로 리드당 1회만** | 상태를 오가도 재발송 없음. `message_logs` 에 (rule_id, lead_id) 로 기발송 확인 |
| **발송 실패** | **로그만 남기고 재시도는 수동** | 자동 재시도 없음. ⚠️ 보완 필요 — 아래 주의 참고 |
| **광고주 권한** | **광고주도 발송 가능. 단 마케터가 권한을 줘야 한다** | 기존 권한 부여 구조(`advertiser_form_grants` 의 `can_export`·`can_status`) 에 **발송 권한 플래그 추가** → Flyway 필요 |

> ⚠️ **실패 처리 주의(설계 시 보완할 것)**: 자동 재시도가 없으므로 대행사 일시 오류에 메시지가 유실될 수 있다. 자동 발송은 실패해도 눈에 보이지 않으니, **발송 이력 화면에 실패 건수를 눈에 띄게 노출**하고(예: 상단에 "최근 실패 3건") 실패 건에 **다시 보내기 버튼**을 둔다. 그래야 수동 재시도가 실제로 작동한다.

## 3. 데이터 모델 (제안)

**다음 Flyway 는 V22.**

```
message_templates                    -- 템플릿
  id, user_id, name, channel(SMS|EMAIL|ALIMTALK)
  subject            -- 메일 제목(문자는 null)
  body               -- 변수키가 박힌 본문. 예: "{{f1}} 님. ..."
  attachments        -- jsonb: [{name, url, size}]  (R2 업로드 재사용)
  alimtalk_template_code  -- 알림톡용 카카오 심사 번호(1단계는 null)
  created_at, updated_at

message_rules                        -- 발송 규칙
  id, user_id, form_id
  trigger_type(ON_SUBMIT|ON_STATUS_CHANGE|MANUAL)
  trigger_status     -- ON_STATUS_CHANGE 일 때 어떤 상태로 바뀔 때인지
  recipient_type(LEAD|MARKETER|ADVERTISER)
  recipient_var_key  -- recipient_type=LEAD 일 때 수신 번호/메일을 담은 항목의 변수키
  template_id
  enabled            -- 템플릿 변수키가 사라지면 자동으로 false
  disabled_reason    -- 왜 꺼졌는지(어느 변수가 사라졌는지까지 담아 화면에 보여준다)
  allow_repeat       -- 기본 false. 규칙별 리드당 1회 원칙의 예외가 필요할 때만 true
  created_by         -- MARKETER | ADVERTISER (광고주가 만든 규칙 구분)
  created_at

advertiser_form_grants.can_send_message   -- 신규 컬럼. 마케터가 켜야 광고주가 발송 규칙을 만들 수 있다
                                          -- (기존 can_export·can_status 와 같은 자리)

message_logs                         -- 발송 이력
  id, user_id, form_id, lead_id, rule_id, template_id
  channel, recipient(마스킹 저장), rendered_body
  status(SENT|FAILED|SKIPPED), error, provider_message_id
  cost                -- 대행사가 알려주면 저장(정산·확인용)
  created_at

form_blocks.var_key                  -- 항목별 불변 변수키 (신규 컬럼)
```

- **리드 답변에 변수키 함께 저장**: 지금 `leads.answers` 는 `{label, value, fieldType}` 인데 `varKey` 를 추가한다. **신규 리드부터** 정확히 매칭되고, 과거 리드는 `label` 폴백으로 처리한다.
- **문자 계정 연동**: `integration_settings` 에 대행사 종류·API 키·발신번호 목록 추가(계정당 1행 구조 유지).
- **발신 프로필**: `form.settingsConfig` 에 `senderPhone` · `senderEmailName` · `replyTo` (마이그레이션 불필요).

## 4. 변수 시스템

1. **변수키 부여** — 항목을 만들 때 `f1`, `f2`, … 를 한 번 부여하고 **이후 절대 바꾸지 않는다. 항목을 지워도 그 키는 재사용하지 않는다**(지운 항목의 키를 새 항목이 물려받으면 과거 리드·템플릿이 엉뚱한 값을 가리킨다).
2. **편집기** — 변수 목록에서 클릭해 삽입한다. 화면에는 `{이름}`, 저장은 `{{f1}}`.
3. **렌더링** — `리드.answers` 에서 `varKey` 로 값을 찾는다. 없으면 `label` 로 폴백.
4. **값이 빈 경우** — 빈 문자열로 치환하고 **로그에 남긴다**. 필수 변수(수신 번호)가 비면 **발송하지 않고 SKIPPED** 로 기록한다.
5. **시스템 변수도 제공** — `{{form.name}}` · `{{lead.createdAt}}` · `{{marketer.name}}` 등.

## 5. ⚠️ 먼저 고쳐야 하는 기존 구조 (조사 결과)

착수 전에 이걸 모르면 설계가 무너진다.

**① `FormBlock.id` 는 안정적이지 않다 — 변수 기준으로 쓸 수 없다**
```java
@OneToMany(..., orphanRemoval = true)          // Form.java
public void replaceBlocks(...) { blocks.clear(); ... }
FormBlock b = new FormBlock();                 // FormBlockDto.toEntity() — id 를 넘기지 않는다
```
리드폼을 한 번 저장하면 **항목이 전부 삭제되고 새 ID 로 재생성**된다. 그래서 숫자 ID 를 템플릿에 박으면 리드폼을 한 번만 수정해도 전부 깨진다(항목명보다 더 위험). → **별도 `var_key` 를 두는 이유.**

**② 리드 답변이 항목명(label)으로만 저장된다**
```json
"answers": [ { "label": "이름", "value": "홍길동", "fieldType": "text" } ]
```
항목 ID·키가 없다. → **`varKey` 를 answers 에 추가**해야 항목명을 바꿔도 과거 리드가 살아난다.

## 6. 단계별 작업 순서

> **2026-08-01 순서 변경 (사용자)**: 알림톡 심사 신청 완료. **메일을 뒤로 빼고 문자 발송부터** 만든다.
> 이유: 문자가 실제로 쓰이는 채널이고 메일은 급하지 않다. 아래 표는 변경된 순서다.

### 문자 발송 시스템의 발송 대상 3종 (2026-08-01 사용자 지정)

| 대상 | 트리거 | 누가 설정하나 | 수신 번호 |
|---|---|---|---|
| **마케터** | 리드 발생 시 | 마케터 | 마케터 계정 연락처 |
| **광고주** | 리드 접수 시 | **마케터가 직접 설정** (광고주가 스스로 켜는 게 아니다) | 광고주 계정 연락처 |
| **고객(리드 본인)** | 마케터가 지정한 트리거 | 마케터 | 리드폼의 연락처 항목(`var_key`) |

- 광고주향 문자는 **마케터가 광고주별로 on/off** 한다 → §2 의 `advertiser_form_grants.can_send_message`(광고주가 *직접* 규칙을 만들 권한)와는 **다른 것**이다. 이쪽은 마케터가 광고주를 *수신자로* 지정하는 규칙이라 별도 권한이 필요 없다.
- 마케터·광고주향은 **시스템 변수만** 쓰면 되므로 M1 없이도 동작한다. **고객향만 M1(`var_key`)이 전제**다.



| 단계 | 내용 | 비고 |
|---|---|---|
| **M1** | `form_blocks.var_key` 추가 + 기존 항목 백필 + 저장 시 유지 · `leads.answers` 에 `varKey` 기록 | **다른 모든 단계의 전제**. 여기가 틀리면 뒤가 다 흔들린다 |
| **M2** | 템플릿 CRUD + 편집기(변수 삽입·미리보기) | 미리보기는 실제 리드 하나를 골라 렌더해서 보여준다 |
| **M3** | **문자 발송** (마케터 계정 연동, 발신번호 선택) | 대행사 어댑터를 인터페이스로 두고 하나부터 |
| **M4** | 발송 규칙 + 트리거(접수 직후·상태 변경) + 발송 로그 화면 | `NotificationService.planDispatches()` 구조를 확장해 붙인다 |
| **M5** | **메일 발송** (우리 도메인 + Reply-To) | 사업자등록 불필요·거의 무료 |
| **M6** | 수동 발송(리드 골라서) · 첨부파일 | BACKLOG F5 와 연결 |
| **M7** | 알림톡 — 마케터·광고주 접수 알림 (심사 통과 후) | **M1 에 의존하지 않는다**(시스템 변수만 씀) → 심사만 끝나면 언제든 붙일 수 있다. 상세 §9 |

## 9. 알림톡 범위 (2026-08-01 사용자 확정)

알림톡은 **문자·메일과 성격이 완전히 다른 채널**로 다룬다. 같은 템플릿 시스템에 억지로 끼우지 않는다.

| 항목 | 알림톡 | 문자 |
|---|---|---|
| **수신자** | **마케터 · 광고주** (계정에 등록된 연락처) | **리드 본인** (`{연락처}` 항목) |
| **내용** | "리드폼이 접수되었습니다" 접수 알림 | 명함·채무금액·문의사항 회신 등 상세 |
| **발신 채널** | **리드팟 채널 하나로 전부** (우리 명의) | **마케터가 자기 계정 연동** (발신번호 사전등록은 마케터 몫) |
| **본문** | 카카오 심사로 **고정** | 마케터가 자유롭게 편집 |
| **변수** | **시스템 변수만** | 리드폼 항목값(`var_key`) |
| **첨부** | 불가 | MMS 이미지 가능 |

### 왜 이렇게 나누는가

- **마케터 준비물이 0** — 알림톡은 우리 채널로 우리가 보내므로 마케터가 채널 개설·심사를 할 필요가 없다. 반면 문자는 발신번호 사전등록이 법적으로 개인 명의라 마케터가 직접 연동해야 한다(§2).
- **개인정보를 카카오로 넘기지 않는다** — 접수 알림에 이름·연락처·**채무금액**을 넣지 않는다. 어떤 리드폼에 몇 건 들어왔다는 사실만 알리고, 실제 값은 리드팟 인박스에서 본다. 심사 통과도 쉬워진다.
- **M1(`var_key`)에 의존하지 않는다** — 리드 답변값을 안 쓰므로 변수 시스템과 무관하다. 카카오 심사만 끝나면 순서와 상관없이 붙일 수 있다.

### 본문 초안 (심사 신청용)

```
[리드팟] 새 리드가 접수되었습니다.

리드폼: #{리드폼명}
접수시각: #{접수시각}
미확인: #{미확인건수}건

리드팟에서 확인해주세요.
```
- 버튼 1개: **리드 확인하기** → `https://app.lead-pot.com/leads`

### 구현 시 주의

1. **변수 표기가 우리와 다르다** — 카카오는 `#{변수}`, 우리 템플릿은 `{{f1}}`. 알림톡 본문은 **심사된 문자열을 그대로 보관**하고 발송 시 대행사 API 에 변수 맵을 따로 넘긴다. 우리 템플릿 편집기로 편집하게 하면 안 된다(본문이 심사본과 달라지면 발송 거부).
2. **`message_rules.recipient_type`** — 알림톡 규칙은 `MARKETER` · `ADVERTISER` 만 허용하고 `LEAD` 는 막는다.
3. **`message_templates`** — `channel=ALIMTALK` 이면 `alimtalk_template_code` 필수, `attachments` 는 비워둔다.
4. **묶음 알림 고려** — 리드가 몰리면 접수마다 알림톡이 터진다. 건당 과금이므로 **리드폼별 N분 묶음**이 필요해질 수 있다. 단 지연 발송은 스케줄러가 필요해 1단계 제외(§2) → 처음엔 건당으로 두고 실사용 후 판단.
5. 비용·준비물·심사 절차는 [BACKLOG.md](BACKLOG.md) H3 참고. 채널 프로필 이미지는 [docs/design/leadpot-logo-640.png](design/leadpot-logo-640.png).

## 10. 문자 대행사 = 솔라피(Solapi) 확정 (2026-08-01, 조사 후)

### 단가 (API 직접 연동 · 부가세 별도)

| | SMS(90byte) | LMS(2,000byte) | MMS | 알림톡 |
|---|---|---|---|---|
| **솔라피** | 13원 | 29원 | 60원 | 8원 |
| 알리고 | 8.4원 | 25원 | 60원 | 별도 계약 |

우리 발송 패턴은 리드 1건당 3건(마케터 SMS + 광고주 SMS + 고객 LMS) → 솔라피 55원 / 알리고 41.8원.
월 리드 2,000건이면 11만원 vs 8.4만원(차액 2.6만원). 솔라피는 월 물량 기준 최대 57.69% 자동 할인.

### 왜 더 비싼 솔라피인가

1. **이 비용은 마케터가 부담한다**(마케터 계정으로 발송) → 우리 원가가 아니다. 단가보다 개발·운영 단순성이 우선.
2. **알림톡도 솔라피로 쏘면 어댑터 코드가 하나**로 끝난다. 알리고는 알림톡이 별도 계약.
3. **발신번호 목록 조회 API**(`getActivatedSenderIds`)가 있다 → 마케터가 등록해 둔 번호를 드롭다운으로 뽑아줄 수 있고, 우리가 명의 서류를 만질 일이 없다.
4. **공식 Java SDK** 제공 → Spring 백엔드에 바로 붙는다.
5. 어댑터 인터페이스로 두므로 단가를 중시하는 마케터용 **알리고는 나중에 추가**할 수 있다.

### 발신번호 설정

법적으로(전기통신사업법 제84조의2) 사전 등록된 번호로만 발송할 수 있다. 등록은 **솔라피 콘솔에서 마케터가 직접** 한다.

| 번호 | 필요 서류 | 난이도 |
|---|---|---|
| 마케터 본인 휴대폰 | 휴대폰 본인인증만 | 즉시 |
| 사무실 유선번호 | 통신서비스이용증명원 | 보통 |
| 법인 명의 번호 | 사업자등록증 + 통신서비스이용증명원(마스킹 없이) | 보통 |
| 남의 번호(광고주 번호로 발송) | 위·수탁계약서 + 위임장 + 위임사 사업자등록증 + 신분증 | 권장하지 않음 |

- 접수 후 5영업일 내 본인확인 전화가 온다.
- ⚠️ **위임(타사 발신번호) 방식은 접었다** — 우리가 대표로 발송하려면 마케터마다 위 서류를 걷어 관리해야 한다(§2 의 판단을 조사로 재확인).

### 리드팟에서의 흐름

```
마케터가 솔라피 API 키를 리드팟에 등록
  → 리드팟이 발신번호 목록 API 조회
  → 리드폼별로 발신번호 드롭다운 선택
```

출처: [솔라피 단가](https://solapi.zendesk.com/hc/ko/articles/360053238434) · [발신번호 API](https://solapi.com/developers/api/senderid) · [타사 발신번호 위임](https://solapi.com/senderid-delegation) · [알리고 문자 API](https://smartsms.aligo.in/admin/api/info.html)

## 11. 발송 계정 구조 — 리드팟 키가 기본 (2026-08-01 사용자 변경)

§10 을 쓴 직후 사용자가 방향을 바꿨다. **마케터가 솔라피 계정을 직접 만드는 게 아니라, 리드팟 API 키로
마케터·광고주가 쓰게 한다.** 그리고 이 기능은 나중에 **마케터 플랜 결제**에 묶는다(유료 기능).

### 자격증명 = 리드팟 계정 하나 (2026-08-02 확정)

**마케터가 자기 키를 등록하는 경로는 뺐다.** V23 에서 컬럼만 만들고 저장할 API·화면을 만들지 않아
실제로는 한 번도 쓰이지 않는 죽은 분기였다. **V24 에서 컬럼을 지우고 코드도 단순화했다.**

```
모든 발송 → 리드팟 시스템 키 → 플랜 한도 검사 대상
```

- 리드팟 키는 **환경변수로만** 둔다(`APP_SMS_SOLAPI_API_KEY`·`_API_SECRET`·`_SENDER_PHONE`). 코드·DB·git 에 넣지 않는다.
- **발신번호만 리드폼별로 덮어쓸 수 있다**(`settingsConfig.smsSenderPhone`). 단 그 번호도 **우리 솔라피 계정에
  사전등록된 번호**여야 한다 — 마케터 번호를 쓰려면 위임 등록이 필요하다(아래 표).
- 우리 비용이므로 **플랜별 월 한도**를 적용한다.

> **나중에 마케터별 키가 필요해지면**: `integration_settings` 에 컬럼을 다시 추가하고,
> `SmsService.resolveCredentials` 에서 마케터 키를 먼저 찾아 쓰고 없을 때만 시스템 키로 떨어지게 하면 된다.
> 그때를 위해 `SmsCredentials.system` 플래그 · `message_logs.system_credential` · 플랜 한도 분기는 남겨뒀다
> (시스템 키로 보낸 건만 한도에 센다 — 마케터 자기 키는 우리 비용이 아니므로).

### ⚠️ 발신번호 제약 (반드시 알고 있어야 하는 것)

전기통신사업법상 **발신번호는 발송 계정에 사전등록된 번호**여야 한다. 우리 키로 보내면 발신번호도 우리 명의다.

| | 발신번호 | 결과 |
|---|---|---|
| **리드팟 키(기본)** | 리드팟 대표번호 | 마케터·광고주 알림은 문제 없다(회신하지 않는 알림). **고객에게 가는 문자는 발신번호가 리드팟 번호**가 되어 고객 회신·수신거부가 우리에게 온다 |
| 리드팟 키 + 마케터 번호 위임 | 마케터 번호 | 마케터마다 위임장·위·수탁계약서·사업자등록증·신분증을 걷어 솔라피에 위임 등록해야 한다(§10) |
| ~~마케터 자기 키~~ | — | **제거됨(V24).** 나중에 되살릴 때의 선택지 |

- **판단 필요**: 고객향 문자에서 발신번호가 리드팟 번호여도 되는가? 마케터는 "명함 내 번호로 오는 전화를 받아달라"는
  문자를 보내므로(§1 예시) 발신번호가 마케터 번호인 게 자연스럽다. → 고객향을 실제로 쓰기 전에 결정해야 한다.
- 그래서 **발신번호는 리드폼별로 지정 가능한 구조**로 만든다. 기본값은 시스템 번호, 위임 등록이 끝난 마케터는 자기 번호를 고를 수 있다.
- 리드팟 번호로 고객에게 보낼 경우 **수신거부 처리와 회신 응대가 우리 몫**이 된다는 점을 잊지 말 것.

### 사용량·과금

- 발송 1건마다 `message_logs` 에 남기고, **월 사용량 = 그 달의 SENT 건수**로 집계한다(별도 카운터를 두면 어긋난다).
- 플랜별 월 상한을 넘으면 `PlanLimitExceededException` (기존 광고주 수 상한과 같은 패턴: `AdvertiserService.checkCanAddAdvertiser`).
- 자동 발송이 한도로 막히면 **조용히 실패하면 안 된다** — `SKIPPED` 로 기록하고 발송 이력 화면에 눈에 띄게 노출한다(§2 실패 처리 주의와 같은 이유).

### 솔라피 API 규격 (조사 확정)

```
POST https://api.solapi.com/messages/v4/send
Authorization: HMAC-SHA256 apiKey=<KEY>, date=<ISO8601>, salt=<랜덤>, signature=<hex>
  signature = HMAC_SHA256(apiSecret, date + salt)
Body: {"message": {"to": "01012345678", "from": "0212345678", "text": "..."}}
```
- 번호는 **하이픈 없이 숫자만**.
- SMS 90byte 초과 시 LMS 로 자동 전환되며 단가가 오른다(13원 → 29원) — 본문 길이를 화면에 표시할 것.

### 리드팟 발신번호를 어떻게 확보하나 (2026-08-01 조사)

**"가상 발신번호를 만들어주는 서비스"는 없다.** 발신번호는 통신서비스 이용증명원이 필요한 실제 개설 회선이어야 한다.
따라서 회선 하나를 개설해 우리 솔라피 계정에 등록한다.

| 방법 | 월 비용 | 등록 난이도 | 수신 |
|---|---|---|---|
| **알뜰폰 회선 (확정)** | **1,490원** (티플러스 평생요금) | 휴대폰 본인인증만 → 즉시 | 가능(안 받으면 됨) |
| 070 인터넷전화(발신전용 개통) | 2,000~5,000원 | 통신서비스 이용증명원 필요 | 불가 |
| 1544/1566/1588 대표번호 | 1~3만원+ | 서류 | 가능 |

**알뜰폰 회선을 권장하는 이유**
1. 가장 싸다 — 문자 단가(13원/건)에 비해 회선 유지비는 무시할 수준.
2. 010 휴대폰 번호는 **본인인증만으로 발신번호 등록이 즉시** 된다(070·1588은 이용증명원 제출 필요).
3. **010 이 열람률에 유리** — 070·1588 발신 문자는 수신자가 광고로 인식해 안 읽는다. 고객향에서는 단가보다 중요하다.
4. 발신전용 070 은 고객 회신이 유실된다. 알뜰폰이면 회신 문자·전화를 확인할 수 있다.

> 알림톡으로 마케터·광고주 알림을 처리하면 **문자가 필요한 건 고객향뿐**이므로 발신번호는 1개로 충분하다.

#### 알뜰폰 회선 개통 절차 (실행용 메모)

발신번호 등록 시 **그 번호로 인증문자가 오므로 단말이 최소 한 번은 필요**하다. 단 새 폰을 살 필요는 없다.

**권장: 지금 쓰는 폰에 eSIM 으로 회선 추가** (물리 유심·기기 추가 불필요)
- 조건: 아이폰 XS 이후 / 갤럭시 Z플립4·폴드4 이후 및 최근 S 시리즈

> 솔라피가 "타인 명의 위임"으로 분류해 위임장·위·수탁계약서·사업자등록증을 요구한다. 같은 명의면 즉시 등록된다.

#### 회선 요금제는 최저가로 (문자 무제한을 살 필요 없다)

**대행사 발송 비용은 회선 요금제와 별개다.** 겹치지 않는다.

| | 알뜰폰 요금제의 문자 | 솔라피 발송 |
|---|---|---|
| 분류 | **P2P** — 사람이 폰에서 직접 | **A2P(기업메시징)** — 서버가 발송 |
| 경로 | 그 회선을 통해 나감 | **솔라피 서버 → 통신사망 직접.** 회선을 거치지 않는다 |
| 과금 | 요금제 포함(무제한) | 건당 별도(13원) |

회선은 문자를 나르는 통로가 아니라 **"이 번호가 내 것"임을 증명하는 명의 증빙**이다. 회선이 할 일은
① 번호 명의 보유 ② 발신번호 등록 시 인증문자 1회 수신, 이 둘뿐이다.
→ **문자 무제한 요금제는 한 통도 쓰이지 않는다. 최저가 평생할인 요금제를 고른다** (확정: 티플러스 월 1,490원).

> 폰에 자동발송 앱을 깔아 무제한 문자로 우회하는 방법은 통신사 약관(상업적 대량발송 금지)에 걸려 회선이 정지되고,
> 발신번호 사전등록 제도를 우회하는 것이라 실서비스로 쓸 수 없다. 대행사 단가는 피할 수 없는 비용으로 본다.
